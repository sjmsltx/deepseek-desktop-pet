# DeepSeekPet 3.0 总方案（2026-09-21 定稿）

> 本文是 3.0 的**总纲**。所有分项判断的原始依据在本目录其他文档（见文末索引），本文只保留决策与可验收内容。

---

## 0. 一句话

桌宠**不重做成 agent**。3.0 = 桌宠作为 **DeepSeek Harness（DSH）的桌面载体**（弱耦合），DSH 负责 agent 能力、桌宠负责角色化呈现与本地能力；两侧靠 **HTTP + 只读镜像**连接。差异化不做在"套壳"上，而做在**桌宠自建的多角色协作层**（多模型圆桌 + 投递可见化 + 成本护栏）。

---

## 1. 定位与边界（三条铁律）

| 归属 | 负责什么 |
|------|---------|
| **DSH** | 模型与提供方配置、工具与技能、工作区、权限与审批、会话与轨迹、插件体系 |
| **桌宠** | 立绘与情绪、语音（朗读/输入）、唤醒与提醒、本地能力（截图/OCR/剪贴板/日程/回忆）、**协作层界面** |
| **适配层**（`dsh_adapter`） | **唯一**知道 DSH 细节的地方：端口、启动令牌、只读解析 `settings.yaml` |

铁律：

1. **单一事实来源 = DSH**：模型/提供方/技能/工作区只有一份，桌宠**只读镜像、不双写**；
2. **`.credentials.yaml` 永不读取**（官方口径是"只写"），密钥由用户自己在界面里填；
3. **不解析 DSH 的前端**：只做宿主窗口，不抓 DOM、不依赖路由与资源名（其资源名带哈希，每次构建都变）。

---

## 2. 目标 / 非目标

**目标**

- G1 桌宠一键把 DSH 作为"面板"呈现在桌面上，且 DSH 升级不破我家功能；
- G2 提供多模型/多角色协作层：像 QQ/微信那样能**私聊、群聊、@、组织讨论**；
- G3 AI↔AI 的投递**可见、可算账、可打断**；
- G4 桌宠自身能力（立绘/语音/本地工具）保持完全独立可用。

**非目标（明确不做）**

- ✗ 把 DSH 插件（TypeScript）写进主干（官方明说会有破坏性变更、插件无沙箱）；
- ✗ 无议题的"自由群聊"（必然刷屏烧钱）；
- ✗ 改 DSH 源码 / 提交补丁（官方目前不接受外部 PR）；
- ✗ 在本地跑大模型当主力（本机显存 8,151 MiB，只够 7B~8B Q4）；
- ✗ 承担商业化（转售、配额、合规）——个人自用定位，费用留在用户侧。

## 3. 架构

```
┌─────────────────────────── 桌宠进程（Python / PySide6）───────────────────────────┐
│  立绘 / 气泡 / 语音 / 唤醒 / 本地能力 / 协作层 UI                                  │
│         │                                                                        │
│         └── dsh_adapter（唯一耦合点：端口 · 令牌 · settings.yaml 只读）            │
└─────────────────────────────────────┬────────────────────────────────────────────┘
                                      │ HTTP（127.0.0.1:3080，带令牌）
                              ┌───────▼────────┐
                              │   DSH 服务      │  ← 模型/工具/技能/工作区/审批
                              └───────┬────────┘
                                      ▲ 只做宿主窗口，不注入
                              ┌───────┴────────┐
                              │ 壳窗口（独立进程）│  pywebview + 系统 WebView2
                              └────────────────┘

协作层（桌宠侧，独立于 DSH）：
  消息日志（单一事实来源，追加式）
    ├─ V1 群聊流（常显：人话）
    ├─ V2 投递轨道（折叠：谁→谁、类型、token、成本）
    └─ V3 后台总线（默认隐藏：心跳/重试）
```

## 4. 协作层设计（3.0 的差异化核心）

### 4.1 统一消息模型（一套吃下三种拓扑）

| 拓扑 | 会话形态 | 投递语义 |
|------|---------|---------|
| 单聊 | `dm:human↔agent`、`dm:agent↔agent` | 定向（仅双方收件箱 + 人类可见） |
| 群聊 | `group:<id>` + 成员表 | 广播（全员收件箱） |
| 讨论/委派 | `thread:<id>` | 定向 + 结果回投父会话 |

消息字段：`id/ts` · `channel_id` · `sender/recipients` · `kind`（speak/ask/reply/delegate/arbitrate/tool/system）· `visibility`（human/meta/debug）· `meta`（model/tokens/cost/latency/parent_id/turn_no）。

**推荐拓扑**：共享追加日志 + 每 agent 收件箱投影 → 可见化天然成立、可回放、可算账、语义只定义一处。

### 4.2 投递可见化：三层，不二选一

> ⭐ **术语澄清（2026-10-03 更名，防同一个 L 字串管三件事 ✗）**：
>
> | 名字空间 | 用名 | 含义 |
> |---|---|---|
> | **视图层** | `V1/V2/V3` | 界面上给人看的三层：V1 群聊流 / V2 投递轨道 / V3 后台总线 ✓ |
> | **存储层** | `L0/L1/L2` | 上下文存储：L0 全文 / L1 摘要层 / L2 工作集（`rt_store` 族 ✓ 不动 ✗） |
> | **架构层** | `桌宠 / 协作台 / DSH` | 三个进程/职责，**不再用 L 编号** ✗ |
>
> ⚠️ M2 契约里已冻结的 `data-layer="L1|L2|L3"` **本件不动** ✗ —— 它与协作台前端、复核脚本同源变更，须**与下一次契约版本同批**改 ✓（不许半拉子 ✗）。

| 视图 | 位置 | 内容 | 默认 |
|----|------|------|------|
| **V1 群聊流** | 群聊主窗口 | 人类要读的语义消息：谁说了什么、结论、请示、@人类 | 常显 |
| **V2 投递轨道** | 右侧可折叠面板 / 独立"投递"标签页 | 结构化投递：谁→谁、类型、模型、耗时、token、成本、父子关系 | 折叠 |
| **V3 后台总线** | 灰色折叠区 | 心跳、重试、内部协调噪音 | 隐藏 |

不把投递全量贴进群聊流 —— 会刷屏且烧钱；两层读的是**同一份日志**，所以不会出现两套数据。

### 4.3 人类可打断 + 成本护栏（默认值建议）

| 机制 | 规则 |
|------|------|
| 人类插队 | 最高优先级注入；仲裁器在下一回合边界**暂停自动轮转**，**暂停后保持暂停并 @人类、不自动恢复**（"继续"必须是显式命令） |
| 回合上限 | 单议题 8 回合 |
| 时长上限 | 单议题 5 分钟 |
| 成本上限 | 单议题 token / 金额上限，触顶即停 |
| 收敛检测 | 连续 2 回合无新信息 → 自动收束出结论 |
| 议题强制 | 无议题+目标+结束条件 → **不许开会** |
| 触顶行为 | 停 + 出结论 + `@人类`，绝不静默烧钱 |

### 4.4 判断依据（诚实标注）

- **事实**：主流大厂的产品都是**单厂商多角色**，没有跨厂商协作产品；唯一近似的 Bloome 查不到独立评测/活跃度。
- **判断（非实证）**：大厂不做跨厂商的动因是"自有权重才能做推理侧优化 + 成本可控 + 平台期动机"（用户补充：公司间本就不好合作）。**个人开发没有这层动机冲突**，所以"大厂不做"推不出"我们不该做"。
- **约束**：将来若对外发布，多厂商 ToS（用你的 key 转发聚合）与费用转嫁会成问题 → "谁付费、用谁的 key"留在**配置层**（LiteLLM/OpenRouter 这类网关正是该抽象层）。
- **参考实现**：AutoGen 的 GroupChat 仲裁策略、ChatDev 的"双人对话链"（避免一上来就五人群聊）、AI Town 的对话可视化手法；**不**照搬 MetaGPT 的重 SOP。

### 4.5 角色数与 API Key 的正确认知

| 设想 | 能省本机内存吗 | 真实影响 |
|------|--------------|---------|
| 同厂商同一 key 多角色共用 | ✗ | 反而更早撞同账号 RPM/TPM 限流 |
| 同厂商多个 key | ✗ | 扩容并发、隔离配额、便于分账（不省内存） |
| 少接角色 | 影响很小 | 省的是 token 成本与墙上时间 |
| 本地跑模型（离线） | ✗ 反而大增 | 这才吃显存（本机 8 GB → 7B~8B Q4） |

结论：闸门要设在**成本与收敛**上，不是设在"内存"上。

## 6. 风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| DSH 破坏性变更打断我们 | 中 | 分层隔离：适配层唯一耦合点 + 能力探测/降级 + 升级后跑 `check-dsh.ps1` |
| 官方**不接受外部 PR** | — | 不能提交补丁让它兼容我们 → **只能自适配**，所以适配层是必需项而非可选项 |
| 官方桌面端成熟、载体失去价值 | 中 | 差异化押在"角色形态 + 本地能力 + 协作层"，不押在"能开窗口" |
| 依赖它未公开的 `/api/*` | 高 | 不作依赖；要用先探测，失败即降级 |
| 多角色成本失控 | 中 | 四道上限 + 收敛检测 + 议题强制 |
| 本机算力不足 | 中 | 云端推理为主；本地模型只到 7B~8B Q4；编排层不占算力 |
| 双 harness 冲突 | 高 | 明确边界：DSH 管 agent 循环，桌宠管呈现与本地能力，记忆/权限各管各的 |

## 附：修订 2（2026-09-21 16:34 决策）

**职责拆成三层，桌宠保持小：**

| 层 | 是什么 | 干什么 | 不干什么 |
|----|--------|--------|---------|
| 桌宠 | 角色本体 | 立绘/情绪/语音/唤醒/本地能力 + **通知器 + 一句话总结 + 入口** | 不做群聊窗口、投递轨道、多角色列表 |
| **协作台（新）** | QQ/微信式协作 UI（独立进程） | 私聊/群聊/@/组织讨论 + 投递轨道（谁→谁·类型·token·成本）+ 每个角色的立绘与声线 | 不碰 DSH 内部、不写 DSH 插件 |
| DSH | agent 能力（弱耦合接入） | 模型/工具/技能/工作区/审批 | 不承担我们的协作 UI |

**为什么协作台独立、不做进 DSH：** 插件进程内无沙箱（隔离差）+ 要跟着它的 React slots 与 API 变（维护高）+ 官方破坏性变更且不接受外部 PR（依赖风险高）+ 我们把命门交出去。独立协作台在隔离性/UI 自由度/维护成本/官方依赖四项上全面占优；将来若要与 DSH 会话联动，走**官方第三方载体接口**（`__DSH_TRANSPORT__.streamBaseUrl`）而非写插件。

**角色四件套（缺一不可）：** 立绘 + 人格 + 模型 + 声线 —— 没有立绘的角色在体验上站不住，而立绘正是我们相对 DSH 的差异化本体。资产管线现成（Seedream 文生图 → rembg 抠图 → 透明 PNG）。起步 2~3 个角色（异构模型才有稳定增益；群聊工程实践建议 ≤3）。

**施工顺序（先做哪个）：**
1. **P0 先做（分支：桌宠 DSH 载体版）**——小、立刻可用、一次验证三件事（弱耦合可行/窗口栈可用/适配层骨架）。
   - P0.1 **已实测零代码方案**：`msedge.exe --app=<带令牌地址>` 得到独立应用窗口（无标签栏地址栏，窗口标题实测 `DeepSeek Harness`）；
   - P0.2 桌宠右键菜单"打开协作台 / DSH 面板" + 位置记忆 + 置顶；
   - P0.3 适配层模块（只读镜像 settings.yaml + 探测 + 降级 + 版本记录）。
2. **P1 主线原型**：消息日志 + 三层可见化（**先用假数据**，不接模型）+ 角色立绘扩产。
3. **P2**：接模型（复用 DSH 提供方）+ 仲裁器 + 四道上限 + 人类插队。
4. **P3 可选**：DSH 插件。
