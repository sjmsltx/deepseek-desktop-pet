主线与分支：职责三层拆分 + 施工顺序

你担心的两件事都是对的：① 协作层塞进桌宠，它就不再是"宠物"；② 角色没有立绘就不可信。结论是把职责拆成三层，桌宠保持小。

2026-09-21 ｜ 分支 = 桌宠的 DSH 载体版 ｜ 主线 = 多角色协作（独立的"协作台"）

01三层职责（拆分的核心）
Layer 1 · 角色本体

桌宠（保持小）

立绘 · 情绪 · 语音 · 唤醒 · 本地能力（截图/OCR/剪贴板/日程）

新增角色定位：通知器 + 一句话总结 + 入口（点一下就打开协作台/DSH 面板）

不做：群聊窗口、投递轨道、多角色列表

Layer 2 · 协作界面

协作台（新，独立进程）

QQ/微信式：私聊 · 群聊 · @ · 组织讨论 · 会话列表

差异化：投递轨道（谁→谁 / 类型 / token / 成本）＋ 每个角色的立绘与声线

不做：不碰 DSH 内部、不写 DSH 插件

Layer 3 · Agent 能力

DSH（弱耦合接入）

模型与提供方 · 工具与技能 · 工作区 · 权限与审批 · 会话与轨迹

只通过 dsh_adapter 接触（端口 · 令牌 · settings 只读）

不承担我们的协作 UI

02为什么"协作台"要独立，而不是做进 DSH
三个候选落位的对比（★越多越好）
维度做进 DSH（插件/UI）塞进桌宠独立协作台
隔离性差（插件进程内、无沙箱）中（同进程，崩了互相拖累）好（DSH/桌宠崩都与它无关）
UI 自由度中（要按它的 React slots 走）中（PySide6 做聊天流偏笨重）最高（Web 技术，立绘/气泡/轨道随便画）
维护成本高（TS + 跟着它 API 变）中低（自包含，改自己就行）
对官方的依赖高（破坏性变更 + 不接受外部 PR）低低（只用到"能起服务"这一层）
长期演进被它绑住中（桌宠会越来越臃肿）自由；将来也能借官方载体接口当"外部面板"
留一条后路 不是"永远不碰 DSH"：官方预留了第三方载体接口（静态桌面页可声明 __DSH_TRANSPORT__.streamBaseUrl）。将来协作台要展示 DSH 的会话，可以走这条官方支持的路，而不是去写插件。

03立绘不是装饰，是"角色的必要条件" - 你的判断成立：没有立绘的角色在体验上站不住；而且立绘正是我们相对 DSH 的差异化本体。 - 所以每个角色 = 立绘 + 人格 + 模型 + 声线 四件套，缺一不可。 - 资产管线现成（TOOLS.md 已记录）：Seedream 文生图 → rembg 抠图 → 透明 PNG；桌宠已有立绘目录结构与渲染路径可复用。 - 起步角色数建议 2~3 个：学术结论是多 agent 唯一稳定的增益来自"异构模型"，而工程实践建议不超过 3 个角色（Azure 架构中心的 group-chat 指引）；人多了既贵又难收敛。

04施工顺序（先做哪个）
先做 · P0
分支：桌宠的 DSH 载体版（小、立刻可用）

为什么先做它：工作量小（粗估半天~1 天）、马上能用、而且一次验证三件事 —— 弱耦合可行、窗口技术栈可用、适配层骨架成型。

P0.1 已实测：msedge.exe --app=<带令牌地址> 直接给出独立应用窗口（无标签栏/地址栏，实测窗口标题 DeepSeek Harness）—— 零代码先跑通。

P0.2 桌宠右键菜单加"打开协作台 / DSH 面板"，记住窗口位置与置顶。

P0.3 适配层模块：只读镜像 settings.yaml + 能力探测 + 降级 + 版本记录。

然后 · P1（主线）
协作台原型 + 投递可见化（先用假数据）

消息日志内核（追加式）→ L1 群聊流 / L2 投递轨道 / L3 后台总线；不接模型，先把 UI 与语义验证透（便宜、快）。

同期做角色立绘扩产（2~3 个角色的四件套资产）。

之后 · P2
接模型 + 仲裁器 + 四道上限

provider 复用 DSH 已配置的提供方；回合 8 / 时长 5 分钟 / token 与金额上限 / 连续 2 回合无新信息即收束；人类插队暂停轮转。

可选 · P3
DSH 插件方向

只在 P0/P1 稳定后再评估。

05一句话结论
给你拍板用 分支 = 桌宠的 DSH 载体版（先做，小）；主线 = 独立"协作台"（QQ/微信式 + 投递可见化 + 角色立绘）；桌宠保持"宠物 + 通知器 + 入口"，不膨胀。
这样三件事同时成立：桌宠不被撑爆、协作层不被 DSH 绑死、角色有立绘站得住。
