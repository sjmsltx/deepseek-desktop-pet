desktop_pet.py 模块化拆分方案

现状诊断 → 拆分阶段 → 风险评估 → 时机建议（2026-08-30）

一、现状诊断

226PetWidget 方法数
~6500单文件行数
85_append_chat 引用次数
4+1已拆模块 / 待拆主文件

事实澄清：项目不是「全单文件」——08-28 起的新系统（好感度引擎 affection_engine.py、回忆日志 memory_events.py、关系面板 affection_ui.py、小游戏 pet_minigames.py、插件 plugin_manager.py、MCP mcp_bridge.py）都是独立模块。

问题是历史主程序：desktop_pet.py 从项目第一天（v6.19）就是单文件，v6.20~v6.25 每版功能继续往里堆（4672 → 6211 行），一直没有停下来拆。属于「老系统单文件 + 新系统模块化」的混合状态。

二、为什么之前没拆（真实原因）

原因说明
开发惯性每版新功能都在主文件里加方法最快，模块化被推迟为「以后再说」，以后一直没来
强耦合226 个方法共享 self 状态（chat_panel/bubble/pet_label/model），拆类会互相传 self，初期判断「拆不如不拆」
缺少回归测试单文件改完直接跑，拆分后没有测试网兜底，怕拆完引入一堆回归

结论：这是执行失误，不是技术不可能。用户明确要求过工程化模块化，主文件没有执行到位。

三、拆分方案（渐进式，4 阶段）

P1 · 无 UI 纯逻辑抽取 低风险

api_client.py — SSE 流式客户端（_post_stream/_on_stream/_ai_worker/_record_api_usage）

tools_executor.py — 15+ 工具执行（_call_*）+ PowerShell 安全执行（_run_ps/_check_dangerous）

memory_store.py — 记忆读写（_save_memory/memorize/记忆管理/摘要压缩）

storage.py — JSON 原子持久化（_atomic_write_json/_load/_save 通用件）

方法边界清晰、不碰 UI 状态，拆完行为不变，风险最低 · 预计主文件 -2000 行

P2 · 聊天渲染器抽取 中风险

chat_render.py — Markdown 渲染（_render_md_into/_split_rich_blocks/_CodeCard/_TableCard）

chat_bubbles.py — 气泡构建（_new_bubble/_attach_bubble_actions/_render_rich）

UI 相关但纯函数化程度高，通过参数传 widget，不依赖 self 全局态 · 预计主文件 -800 行

P3 · 信号槽与子窗口整理 中风险

chat_panel.py — 聊天面板（_open_chat_panel/输入/历史/导出）

dialogs.py — 记忆管理/提醒管理/关系面板等子窗口

涉及布局与信号连接，需要逐窗口手工验证

P4 · PetWidget 按 Mixin 瘦身 高风险（可选）

AnimationMixin（动画/立绘/动作）· TrayMixin（托盘/热键/自启）· CareMixin（主动关心/唤醒）

同实例多 Mixin 共享状态，需要谨慎处理初始化顺序；若 P1-P3 已完成，主文件已降至 ~2500 行，P4 可缓

四、风险评估与对策

风险对策
拆分引入回归 bug每阶段拆完跑 smoke_test + 手工验证核心链路（对话/工具/记忆/主动关心），确认无回归再进下一阶段
v6.40 流式修复未稳建议先确认 emotion 泄漏/思考折叠验证通过，再动架构，避免「新 bug + 架构变动」叠加排查
模块间循环 importP1 模块只被主文件 import，单向依赖；P2+ 通过参数注入 widget，不反向 import 主文件
git 历史混乱拆分提交只做「移动代码」，不夹带功能改动，保持可回溯

五、工作量与时机

阶段预计主文件剩余
P1 纯逻辑半天（含回归）~4500 行
P2 渲染器半天~3700 行
P3 子窗口半天~2800 行
P4 Mixin（可选）1 天~2000 行

建议时机：先完成 v6.40 修复验收 → 再启动 P1（低风险起步）→ 每阶段验证后推进。用户拍板是否现在开始。
