DeepSeekPet × DSH · 3.0 风险分析

它升级了，会不会把我们要做的东西打断？

答案取决于你依赖它哪一层：只做"宿主窗口"几乎不受影响；一旦去解析它的配置、接口或界面，就会被更新打断。下面是我们**实测出来的依赖面**与对应的抗变设计。

2026-09-21 ｜ 实测对象：本机 DSH 0.1.5-rc.2（127.0.0.1:3080）｜自检脚本 D:\dsh\check-dsh.ps1

01我们的实际依赖面（逐条实测）
风险等级：低 = 更新几乎不会碰；中 = 可能变，需适配层；高 = 明说会变，不作依赖
依赖面我们的用法实测证据更新风险抗变设计
启动命令与端口 dsh web，127.0.0.1:3080 CLI 帮助里是文档化选项（--port/--host/--no-open） 低 端口做成可配置；地址不写死在内核，只在启动器里
带令牌的访问地址 从启动输出里读 ?token=…，再开窗口 每次启动令牌不同；check-dsh.ps1 已能自动核对 中低 只封装在 start-dsh.ps1 一处；格式变了只改这一处
宿主窗口（把界面装进桌宠） 只做"打开/嵌一个窗口"，不解析页面 它的前端是插件动态装配：/plugins/??@deepseek-ai/dsh-client-ui-*&rev=<哈希> —— 资源名带哈希，每次构建都变 低（前提是不注入） 只做宿主，不做注入：不抓 DOM、不依赖路由、不读资源文件名
设置文件 $DSH_HOME/settings.yaml 只读镜像（模型/提供方清单展示） 官方文档明确"模型页写的就是这份文档"，并给了字段说明 中 适配层 + 存在性/格式探测 + 读不动就降级为"打开它的设置页"
凭据文件 .credentials.yaml 不读（官方口径是只写） 自检只做存在性检查，绝不读内容 低 永不依赖；密钥由用户自己在界面里填
未公开的 /api/* 目前不用 /api、/api/health → 401（存在，但无公开文档） 高 不作为依赖；真要用先做可用性探测 + 失败即降级
DSH 插件（TypeScript） 已降为可选项 插件跑在沙箱外、进程内；官方明说有破坏性变更 高 不作为主干；只在载体稳定后再评估

02三层隔离：把"会变的东西"关进一扇门
适配层adapter
桌宠内核不认识 DSH 的任何细节；只有 dsh_adapter 这一个模块知道端口怎么配、令牌怎么取、配置怎么读。它变了 → 只改这一个文件。
能力探测 + 降级probe & degrade
每次启动探测：服务在不在、令牌是否有效、配置是否读得动。缺什么就隐藏对应功能，绝不崩、绝不假装成功。
界面层：只做宿主host only
窗口只负责"装"它的页面。它把界面全改了，我们这边零改动——顶多视觉变了。

03最坏情况：它大改甚至停更
做法DSH 大改 / 停更时会怎样
弱耦合（我们现在选的） 桌宠自身功能全部照常：立绘、语音、本地工具、记忆、桌面能力。受影响的只是"DSH 面板"这一块，且只需改适配层一处。
深度融合（写进它的插件体系） 它一改 = 我们跟着崩；它停更 = 我们停在旧版本上进退两难。这就是我们把它降为可选的原因。
一条被忽略的强制条件 官方不接受外部 PR ➜ 我们不能"提交补丁让它兼容我们"，只能自己适配。 所以"适配层 + 探测降级"不是可选项，而是这套方案能长期活着的前提。

04升级后的应急流程（已脚本化） 
powershell -ExecutionPolicy Bypass -File D:\dsh\check-dsh.ps1

输出会明确告诉你哪一层断了：

  • 载体层绿 → 桌面载体不受影响，照常做；
  • 载体层断 → 只改 start-dsh.ps1 里"取带令牌地址"的那几行；
  • 配置层断 → 只改适配层里读配置的部分，并降级为"打开它的设置页"。

当前实测：载体层 ✓（HTTP 200 / 27,660 字节）、版本 0.1.5-rc.2、配置层文件均在（只做存在性检查，不读内容）。

05结论
一句话 不会被打断 —— 前提是我们坚持"只做宿主、只读它文档化的东西、其余全部走适配层"。
真正会被更新打断的不是"弱耦合"，而是"偷偷去解析它的内部结构"：界面资源名带哈希、插件 id 会改名、配置文件格式在 preview 期会变、/api 没有公开文档 —— 这些一旦被我们依赖，升级就是一次事故。
