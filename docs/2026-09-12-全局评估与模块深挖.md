## 二、仓库体检：8.78 GB 里有 8.5 GB 是孤儿 pack

### 2.1 事实

```
.git 总占用                    8.78 GB
.git/objects/pack             8.71 GB
  .pack 42 个（每个 ≈223 MB）
  .idx  42 个（每个 0.02–0.03 MB）
  .rev  42 个 + multi-pack-index 1 个
```

三个独立口径互相矛盾，指向同一真相：

| 口径 | 数值 |
|---|---:|
| `git count-objects -vH` → `in-pack` | 35,581 个对象条目 |
| `git cat-file --batch-all-objects` → **唯一对象** | **985 个** |
| `git rev-list --objects --all` → 可达对象 | 981 行 |
| 跟踪文件总体积 | 189.2 MB |
| `git fsck` | rc=0，仅 1 个游离 blob，**无 `.keep` 文件** |

**推断**：`count-objects` 是把 42 个索引里的对象**累加**（42 × ≈847 ≈ 35,581），而按 SHA 去重后只有 985 个——也就是**同一份历史被复制了约 36 遍**。这与你一直看到的 `could not write multi-pack-index` / `failed to perform geometric repack` 是同一个病灶：多 pack 写出来了，旧 pack 没删掉，一次一次叠成了 8.7 GB。

### 2.2 另一笔账：182 MB 立绘资产

| 目录 | 体积 | 文件数 |
|---|---:|---:|
| `assets/` | **182.16 MB** | 112（PNG） |
| `screenshots/` | 6.33 MB | 19 |
| 全部跟踪文件 | 189.2 MB | 215 |

单张立绘 **2.4–3.9 MB**（最大的 `assets/pro/pro_sing.png` = 3.85 MB）。桌宠立绘在屏幕上最多显示几百像素，这个体积是**10 倍冗余**；而且每改一次图，历史里就再存一份完整副本——这是 pack 能到 223 MB 的直接原因。建议 `pngquant`/`oxipng` 压缩或按显示尺寸缩放（通常能降到 200–400 KB），若不想改历史可先做增量优化。

**已执行（2026-09-12）**：按"显示尺寸 260 px（`pet_size`）"重定尺寸——长边 2048 / 2476 → **1024**（显示尺寸的 4 倍，HiDPI 充裕），LANCZOS 重采样 + `optimize=True`，Live2D 贴图不动。

| 指标 | 结果 |
|---|---|
| `assets/` 总体积 | **248.3 MB → 93.5 MB**（省 154.7 MB，62%；122 张里压缩 121 张） |
| 感知质量（合成实底后在显示尺寸比较） | **RMSE 0.53–0.62 / 255**；520 px（2x）下 0.63–0.81 —— 肉眼不可辨 |
| 回归验证 | `regression_test` 40/40；`QPixmap` 载入正常（1024×1024） |
| 原件 | 已移到备份目录 `立绘原图-压缩前/`，随时可回滚 |
| 还能再省 | 若接受轻微色带，再叠 256 色调色板量化可到 ~30 MB 量级（本轮未做，留给你决定） |

### 2.4 已执行的清理动作（2026-09-12 当日完成）

```
# 0. 备份：bundle 完整历史 + refs/计数/提交表快照（备份目录 desktop-pet-git备份-20260912）
git bundle create ...\desktop-pet-full-history.bundle --all
# 1. 合并所有 pack，删除冗余旧 pack
git repack -ad
# 2. 清掉已打包的松散对象
git prune-packed
# 3. 校验
git fsck --full --no-progress
git count-objects -vH
```

| 步骤 | 实际结果 |
|---|---|
| 备份 | `desktop-pet-full-history.bundle` **223.3 MB**，`git bundle verify` = "The bundle records a complete history" ✅ |
| `git repack -ad` | **失败**（退出码 128，耗时 641.7s）：`fatal: failed to clear multi-pack-index`——但**新 pack 已成功写出**（`pack-543ddff6…`，223.33 MB / 984 对象，`verify-pack` 链校验 ok） |
| 手工收尾 | 42 份冗余 pack（127 个 pack/idx/rev）+ 失效 MID 移出到备份目录，保留新 pack 与松散对象 |
| `git fsck --full` | **rc=0，无缺失对象** ✅ |
| `git count-objects -vH` | `packs: 42 → 1`、`size-pack: 8.71 GiB → 223.35 MiB`、`garbage: 0` |
| `.git` 总体积 | **8.78 GB → 0.22 GB（回收 8.56 GB）** |
| 清理后回归 | `regression_test.py` 39/39、`tests/test_command_gate.py` 105/105 ✅ |

**根因（比"pack 是孤儿"更准确）**：`git commit` 会自动触发
`git maintenance run --auto` → `git repack -d -l --cruft --write-midx`。
在这个 8.7 GB / 42 份重复 pack 的仓库上，后台维护每次都要重写 multi-pack-index，
而它与前台 git 操作**互相抢同一个 MID 文件**——这正是长期报的
`could not write multi-pack-index: Permission denied` / `failed to perform geometric repack`，
也是"E 盘提交要等 60 秒+"的同一来源（源码注释里已记过这个卡顿）。
清理后仓库只剩 1 个 pack，维护动作又快又不会撞车。

> ⚠️ 遗留：被移出的 42 份冗余 pack（约 8.9 GB）**暂存在备份目录未删除**，
> 确认桌宠运行一段时间无异常后删掉即可真正释放磁盘。
> 完整历史有 223 MB 的 bundle 兜底，随时 `git clone` 它就能还原。

`remember_fact` 用毫秒时间戳做 ID（同毫秒撞车，第二条会覆盖第一条）；`feed` 用存储的静态 `satiety` 而非衰减值（久不喂一次回满）；原子写在 `affection_engine`/`memory_events`/小游戏**各写一遍**，而小游戏存档**压根不是原子写**；`care_engine.judge_wakeup` 裸 `except: pass`（网络故障与"AI 不想打扰"无法区分）；`run_ps(skip_check=True)` 路径完全无校验。

### 5.3 🟢 低

`code_checker` 临时文件名固定（并发互相覆盖 + 崩溃残留）；`memory_events` 回忆 ID 取模约 166 分钟回绕一次；`read_clipboard` 把剪贴板内容送入模型上下文且无隐私提示。

### 5.4 建议的收敛路径（顺序很重要）

```
1. 把 check_dangerous 从黑名单改成白名单（只放行只读查询类 cmdlet）
2. 三处裸拼 shell 改为参数化调用：subprocess.Popen([...], shell=False)
   open_app 用 webbrowser.open(url) / os.startfile(path)，并校验 scheme ∈ {http, https}
3. calculate_expr 改用 ast 白名单求值 + 指数上限 + 长度上限
4. 兜底：所有工具执行前，把「将要执行的原样命令」展示给用户确认（现在只有一个工具走确认）
```
