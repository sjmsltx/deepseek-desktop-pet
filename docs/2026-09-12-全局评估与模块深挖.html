01摘要

项目结构已经成型、可继续扩展，但有一批"不致命、却持续放血"的问题：仓库白占 8.5 GB、安全边界形同虚设、人设规则静默丢失、宿主类开始变重。按优先级排序，最重的五项是：

#问题性质代价
1仓库 8.78 GB 中约 8.5 GB 是 42 份近似重复的 pack工程卫生每次 gc 报错、clone/备份极慢
2AI 可执行命令的黑名单可被大量绕过；eval 可被一次表达式打挂安全提示注入 → 执行任意命令
3model_registry 用裸 float() 解析用户可编辑的 models.json稳定性手滑一个字段 → 桌宠起不来
4prompt_builder 的 role_anchor 是死代码功能静默回归"你是谁"人设规则一直没生效
5desktop_pet.py 一个类 5,889 行 / 252 方法 / 402 个 self 属性架构加功能的边际成本快速上升

前四项都是几行到几十行就能修的，第五项需要分阶段拆。

03二、仓库体检：8.78 GB 里有 8.5 GB 是孤儿 pack

2.1 事实

.git 总占用                    8.78 GB
.git/objects/pack             8.71 GB
  .pack 42 个（每个 ≈223 MB）
  .idx  42 个（每个 0.02–0.03 MB）
  .rev  42 个 + multi-pack-index 1 个

三个独立口径互相矛盾，指向同一真相：

口径数值
git count-objects -vH → in-pack35,581 个对象条目
git cat-file --batch-all-objects → 唯一对象985 个
git rev-list --objects --all → 可达对象981 行
跟踪文件总体积189.2 MB
git fsckrc=0，仅 1 个游离 blob，无 .keep 文件

推断：count-objects 是把 42 个索引里的对象累加（42 × ≈847 ≈ 35,581），而按 SHA 去重后只有 985 个——也就是同一份历史被复制了约 36 遍。这与你一直看到的 could not write multi-pack-index / failed to perform geometric repack 是同一个病灶：多 pack 写出来了，旧 pack 没删掉，一次一次叠成了 8.7 GB。

2.2 另一笔账：182 MB 立绘资产

目录体积文件数
assets/182.16 MB112（PNG）
screenshots/6.33 MB19
全部跟踪文件189.2 MB215

单张立绘 2.4–3.9 MB（最大的 assets/pro/pro_sing.png = 3.85 MB）。桌宠立绘在屏幕上最多显示几百像素，这个体积是10 倍冗余；而且每改一次图，历史里就再存一份完整副本——这是 pack 能到 223 MB 的直接原因。建议 pngquant/oxipng 压缩或按显示尺寸缩放（通常能降到 200–400 KB），若不想改历史可先做增量优化。

2.4 建议动作（需你确认后我再执行）

# 0. 先备份 .git（8.8 GB，务必先备份再动）
# 1. 合并所有 pack，删除冗余旧 pack
git repack -ad
# 2. 清掉已打包的松散对象
git prune-packed
# 3. 校验：对象数、历史条数、回归测试
git fsck --no-progress
git count-objects -vH      # 预期 size-pack 从 8.71 GiB 降到 ~0.23 GiB

风险提示：若这些 pack 的索引有损坏（git verify-pack 对它们报 bad），repack 可能中途失败；失败不要紧，因为对象齐全（fsck 通过），届时改用手工保留最新 pack 的方式清理。这一步我不会擅自执行——要不要清、什么时候清，你定。
