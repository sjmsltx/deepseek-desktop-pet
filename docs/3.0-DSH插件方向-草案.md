# 3.0 方向草案：与 DSH 高度耦合的桌面端（仅记录 · 未设计）

> 记录时间：2026-09-19 · 提出人：李滨宇 · 状态：**待专门讨论**，本轮不做任何设计与实现

## 一、原始设想（原话要点）

- 3.0 要**开一个分支**，这个分支实现与 **DSH 的高度耦合**。
- 更准确地说：**直接做成 DSH 的插件**。
- 该插件要能做到：**让 DSH 的网页端直接变成桌面形态**（像桌宠这样的桌面版本）。
- 并且能**接入用户已有的 DSH 其他插件**，或调用 DSH 的其他功能。
- 用户明确：这件事"涉及非常大的版本/功能更新"，**先记下来，不要忙**。

## 二、我理解的目标（待确认，不是结论）

1. **形态**：把 DSH 的 Web 界面"搬"到一个常驻桌面的外壳里（桌宠式交互 + 完整功能界面），而不是现在这种"桌宠 + 内置聊天"的独立应用。
2. **关系**：桌宠从"自带 AI 客户端"变成"D SH 的一个桌面插件/宿主外壳"——AI 能力、插件体系、会话与账号都来自 DSH，桌宠负责桌面形态与本地能力。
3. **互通**：用户已有的 DSH 插件（工具/技能）能在桌面外壳里直接可用；桌宠现有的本地能力（热键、语音、图片、WPS/COM、本地文件、MCP）反向提供给 DSH 侧。

## 三、必须先想清楚的几个问题（讨论题，不是方案）

| # | 问题 | 为什么关键 |
|---|---|---|
| 1 | **主体是谁**：桌宠作为插件嵌进 DSH，还是桌宠作为宿主把 DSH 前端装进来？ | 决定了代码归属、升级方式、权限边界 |
| 2 | **插件协议由谁定义**：DSH 官方插件 API 是否开放/稳定？我们只能适配还是可以扩展？ | 决定可行性；若协议不开放，只能做"外壳 + 浏览器控件"这类弱耦合 |
| 3 | **账号与数据**：会话、文件、权限跟 DSH 走还是本地双份？ | 涉及隐私与合规，也决定迁移成本 |
| 4 | **与现有桌宠的关系**：共存（两条产品线）还是演进（2.x 成为 3.0 的兼容层）？ | 决定是否要背 2.x 的包袱 |
| 5 | **桌面形态的边界**：是把网页套个壳（WebView/CEF），还是把 DSH 前端代码拿下来本地渲染（Electron/Tauri/QtWebEngine）？ | 性能、体积、离线能力、更新机制差异巨大 |
| 6 | **本地能力怎么暴露**：热键/麦克风/剪贴板/COM/MCP 通过什么桥接给 DSH 侧（本地 HTTP？WebSocket？插件 RPC？） | 这是"桌面版"真正的增量价值所在 |
| 7 | **分发与审核**：DSH 插件市场是否需要审核？我们的本地能力（执行命令、读文件）能不能通过审核？ | 影响产品边界与安全叙事 |

## 四、下一步（等用户回来定）

1. 先调研 **DSH 插件体系的官方文档/示例**（能力范围、协议、生命周期、发布方式）—— 这是可行性前提，不调研完不动手。
2. 调研 **桌面壳技术选型**：Qt WebEngine（项目已在用 PySide6，可能复用）/ Tauri / Electron，对比体积、安装、调试、与现有 Python 侧能力互通。
3. 出一份"3.0 可行性 + 架构方案（含图示）"，再讨论要不要开分支。
