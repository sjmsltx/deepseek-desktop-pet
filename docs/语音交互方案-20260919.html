语音交互方案：让桌宠开口、也能听你说话

这是 README 路线图 B 项目里唯一还空着的「语音交互（TTS/ASR）」。本方案先把可行性测实了 —— 本机 WinRT 内置中文声线与中文识别包**都已就绪、零额外依赖**，而且可以复用桌宠现成的 PowerShell+WinRT 套路（OCR 就是这么做的）。

一、可行性实测（本机，2026-09-19）

① SAPI（离线，零依赖）：Microsoft Huihui Desktop(zh-CN,女) · Microsoft Zira(en-US,女) —— 能用但机械
② WinRT 合成（离线，零依赖）：Microsoft Huihui / Yaoyao(女) / Kangkang(男) —— 比 SAPI 自然，仍是系统内置
③ WinRT 识别语言包：zh-Hans-CN（简体中文·中国大陆）已安装
④ WinRT 识别实例：创建成功，当前语言 zh-Hans-CN ✓
⑤ edge-tts 7.2.8：桌宠可用的 python 里已装（在线，声线质量最好，如 zh-CN-XiaoxiaoNeural）

结论：**离线语音这条路在本机是通的，且不需要用户额外装任何东西**。桌宠已经在用同一套路做 OCR（`ocr_helper.ps1` 调 WinRT），语音只需照抄这个模式加两个小脚本。

二、选型：合成（TTS）

方案依赖 / 联网质量延迟评价
WinRT 内置声线零依赖 离线中上（3 个中文声线）低（<0.5s）默认选项：免安装、不联网、隐私好
SAPI零依赖 离线较机械低兜底（WinRT 不可用时的退路）
edge-tts（已装 7.2.8）需联网 + 包最好（晓晓/云希等）中（首次 ~1s）可选升级：设置里给「离线声线 / 在线高质量」两档，默认离线
云 TTS（Azure 等）需 key + 计费最好中不做（增加账号与成本，与「本地优先」相悖）

三、选型：识别（ASR）

方案依赖 / 联网中文效果体积评价
WinRT 语音识别零依赖 离线（本机语言包已装）日常短句可用0（系统自带）P1 默认：与 OCR 同一套路，免装免下载
faster-whisper（本地）pip 包 + 模型下载更好（长句/口音）模型 100~300MB+P2 可选增强；打包体积会涨，先不做
云 ASR需 key + 计费 + 上传音频最好0不做（隐私与成本）

四、架构与流程（沿用现有模块化风格）

新增 1
tts_helper.ps1
PowerShell + WinRT 合成：文本 → wav 文件（写临时目录）。仿照 `ocr_helper.ps1`，Python 侧用 subprocess 调，返回路径给播放器。
新增 2
asr_helper.ps1
PowerShell + WinRT 识别：麦克风 → 文本（单轮，静音自动结束）。同样是子进程调用，超时可杀。
新增 3
voice_io.py
统一入口：`speak(text)` / `listen(timeout)`；带播放队列（不打断当前朗读）、夜间静音、失败降级到 SAPI 并回报错误。
接线
主程序 3 处
① AI 回复完成 → 剥掉 [emotion:xxx] 标签后朗读；② 右键/设置加「🔊 朗读回复」「🎤 说句话」；③ 设置加开关（默认关）+ 声线选择。

朗读时序（输出）

AI 流式回复结束 → 剥标签/去 Markdown 符号 → 文本分句（按标点切） → 逐句合成+播放（可打断）
                     ↘ 同步气泡显示（既有逻辑不动）
夜间（23:59–08:00）或开关关闭 → 直接跳过，不产生任何子进程

语音输入时序（输入）

用户按热键 / 点「🎤 说句话」→ 提示「正在听…」（状态条，带明确指示）→ WinRT 识别（静音自动结束）
  → 识别文本**填入输入框而不是直接发送**（保留你最后确认的一步）→ 你按回车才发出去

五、分阶段（建议只批 P0+P1）

阶段内容工作量验收
P0 朗读 AI 回复自动/手动朗读；离线 WinRT 声线（SAPI 兜底）；夜间静音；剥标签与 Markdown 清洗；播放队列不打断 约半天 开关生效；连续两条回复不会叠着播；关掉开关后**零子进程**；夜间静音生效；新增测试覆盖清洗与队列
P1 语音输入 热键 + 按钮 → 识别 → 填入输入框（不自动发送）；状态条明确提示正在听；超时可中止 约一天 识别文本进输入框且不自动发；未装语言包/无麦克风时给出明确提示而不是静默失败；有测试覆盖失败路径
P2 增强（先不做） 唤醒词、边说边识别（流式）、口型联动、whisper 本地增强 视情况 —

六、风险与边界（我建议的默认值）

问题处理
麦克风隐私**默认关闭**；只在按下热键的那几秒打开麦克风；听的时候状态条明写「正在听…」；不录音留存（识别完即丢临时文件）
打扰（突然出声）朗读**默认关闭**，由用户主动开；夜间（23:59–08:00）强制静音（沿用 TTS 既有思路）
打包体积P0/P1 全部走系统 WinRT/SAPI → **不增加任何依赖与体积**；edge-tts 只在源码运行且用户显式选择时用
非 Windows项目本就深绑 Windows（winmm / 注册表自启）；语音同样只做 Windows，其他平台降级为「不显示该功能」
成本语音输入会**多花 token**（同样一句话，语音识别文本可能更长）——统计里能看到，且语音只在你主动用时发生
识别准确率WinRT 识别是「够用」级别；识别错了你可以在输入框里改完再发（这也是不自动发送的原因）

要你定的三件事：① 是否按 P0 朗读 → P1 语音输入 的顺序做（我建议先只做 P0，你听几天再决定要不要语音输入）；② 离线声线（WinRT，免装）还是在线高质量（edge-tts，需联网）；③ 朗读默认开还是默认关（我建议**默认关**，避免打扰和误会）。

七、第二项待办：记忆检索（「搜共同经历」）草案

现状：回忆相册已有「按类型浏览」，记忆注入也有 BM25+重排；缺的是**面向用户的检索入口** —— 你想找「那次一起玩扫雷的事」得自己翻。

要做的事做法（沿用现有引擎，不新建体系）
入口回忆相册里加搜索框；聊天面板支持 `/回忆 关键词`
检索复用 `memory_engine.search_memory_for_injection`（BM25 + 闸门 + LLM 重排），只换「展示」不换「引擎」
展示命中条目 + 时间 + 类型（事实/事件）+ 相关度；点击可回到当时的对话片段
工作量约半天，风险低（纯读操作，不改记忆写入逻辑）

这一项比语音小得多，也可以直接排在语音 P0 之前做 —— 由你定顺序。
