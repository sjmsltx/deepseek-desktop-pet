02主线：桌宠作为 DSH 桌面载体（弱耦合）

这条主线被确认，理由不是"套壳简单"，而是"套壳这条路上官方和第三方都已经占了，我们的增量在别处"。

事实含义
官方已自带 apps/desktop（Electron 壳，端口 19387）"把网页端做成桌面形态"官方做完了 → 单纯套壳没有增量
第三方已有 hairyf/deepseek-harness-desktop、LambProgrammer/dsh-desktop-zero门槛不高且已有人走 → 差异化必须来自别处
官方预留第三方载体接口：__DSH_TRANSPORT__.streamBaseUrl，原文 "The desktop carrier owns authentication"官方明确支持第三方承载 → 做载体是"被支持的正道"
DSH 插件 = TypeScript 模块（apply(ctx)），无沙箱，跑在 workspace sandbox 之外、进程内强耦合路线安全面与维护面都不划算 → 不当主线

我们的差异化（不是"再做一次套壳"）

  • 形态：别人给"窗口里的网页"，我们给有立绘、有情绪、有记忆的角色，DSH 会话嵌在这个角色里。
  • 本地能力：桌宠已有的截图 / OCR / 剪贴板 / 日程 / 语音 / 好感度 / 回忆，是纯 Web 端拿不到的东西。
  • 渐进：载体走 HTTP 弱耦合（127.0.0.1:3080），DSH 升级不影响我们；插件路线要跟着 TS API 变动走。

04反向证据的再解读（他说得对）

我原来把"大厂都做单厂商多角色"当作反向证据；他的解读补上了动因层。

解释是否成立说明
公司之间本身就不好合作，所以不做跨厂商成立（他给的）跨厂商协作对平台方 = 替对手优化 + 承担对方 API 的不确定性
商业化 / 成本考量成立（我原来的猜测）自有权重才能做推理侧优化、成本可控
我们个人开发不需承担这些风险成立只做 provider 接口 + 协调层；钱和合规留在用户侧
必须标注的边界 以上三条是判断与推演，不是实证 —— 无公开一手材料证明大厂的取舍动因。
另有一条真实约束：若将来对外发布"多模型圆桌"，多厂商 ToS（用你的 key 转发聚合）与费用转嫁会成为现实问题 → 应把"谁付费、用谁的 key"留在配置层（LiteLLM / OpenRouter 这类网关正是这个抽象层）。

05不只群聊：统一消息模型

要的是"像 QQ/微信"——能私聊、能群里 @、能组织讨论。这要求一套消息模型吃下三种拓扑，而不是做三个功能。

拓扑会话形态投递语义
单聊dm:human↔agent、dm:agent↔agent定向投递（仅双方收件箱 + 人类可见）
群聊group:<id> + 成员表广播投递（全员收件箱）
讨论 / 委派thread:<id>（挂在群或单聊下）定向 + 结果回投父会话
推荐拓扑 共享追加日志（single source of truth）+ 每 agent 收件箱投影。 理由：① 可见化天然成立（日志就是 UI 数据源）② 私聊 / 群聊 / 线程统一 ③ 可回放、可审计、可算账 ④ 投递语义集中一处定义，不会三套逻辑打架。

06投递可见化：分三层，而不是二选一

问题是"在群聊里直接贴出来，还是单独列一个消息栏？" —— 两个都要，但分层，且同源。

L1 群聊流常显
人类要读的语义消息：谁说了什么、结论、请示、@人类。位置：群聊主窗口。
L2 投递轨道折叠可展开
结构化投递事件：谁 → 谁、类型（提问/回答/委派/仲裁/工具）、模型、耗时、token、成本、父子关系。位置：群聊右侧可折叠面板，或独立"投递"标签页。
L3 后台总线默认隐藏
心跳、重试、内部协调噪音。位置：灰色折叠区，仅调试时展开。

为什么不全量贴进群聊流：担忧是对的 —— AI 互聊会刷屏且烧钱。L1 只保留"面向人类的消息"，机器之间的投递元数据进 L2；两边读的是同一份日志，因此不会出现两套数据不一致。

投递示例　pro ──ask──▶ mao 　｜　mao ──reply──▶ pro（回投父会话）　｜　系统 ──arbitrate──▶ 群（第 3 回合起收敛）

建议的数据模型（每条消息一行）

字段说明
id / ts单调递增 + 时间戳（排序与回放依据）
channel_id群 / 单聊 / 线程
sender / recipientshuman:owner、agent:pro、system；收件人为空 = 广播
kindspeak 发言 / ask 提问 / reply 回答 / delegate 委派 / arbitrate 仲裁 / tool 工具调用 / system
visibilityhuman 进 L1 ／ meta 只进 L2 ／ debug 只进 L3
metamodel、tokens、cost、latency、parent_id、turn_no

最小实现：桌宠/壳里做一个"投递轨道"面板，用箭头渲 sender → recipients，颜色区分 kind，点开看原文与成本 —— 这一步完全在本地做，不依赖 DSH。

07人类可打断与成本护栏

机制规则
人类插队人类消息 priority=highest：立即注入当前会话，仲裁器在下一个回合边界暂停自动轮转，暂停后保持暂停并 @人类、不自动恢复（"继续"必须是显式命令；原"超时自动恢复"口径已作废）
回合上限单议题最大回合数（建议默认 8）
时长上限单议题最长墙钟时间（建议默认 5 分钟）
成本上限单议题 token / 金额上限，触顶即停
收敛检测连续 2 回合无新增信息 → 自动收束并输出结论
议题强制群聊必须有议题 + 目标 + 结束条件才能开（禁止无题自由群聊）
触顶行为停 + 出结论 + @人类；绝不静默继续烧钱

明确"做不到"的事（不粉饰）

  1. ✗ 本地跑圆桌不等于不花钱 —— 推理仍在云端 API，本地省的只是编排与 UI。
  2. ✗ 本地跑 30B+ 级模型 —— 8 GB 显存不够；可行档位是 7B~8B Q4（能跑但速度一般）。
  3. ✗ 现在就直接升 DSH —— VM 不可达，需先确认其位置与启动方式。
  4. ✗ 把无沙箱的 DSH 插件当主线 —— 安全面与维护面都不划算。
  5. ✗ 同频跑"本地大模型 + DSH VM + 桌宠 + 浏览器" —— 15.7 GB 内存会紧张。
