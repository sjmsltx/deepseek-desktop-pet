## 二、主线：桌宠作为 DSH 桌面载体（弱耦合）

### 为什么这条是主线

| 事实 | 含义 |
|------|------|
| DSH 官方**已自带** `apps/desktop`（Electron 壳，端口 19387） | "把网页端做成桌面形态"官方做完了 → 单纯套壳**没有增量** |
| 第三方已有两个桌面壳：`hairyf/deepseek-harness-desktop`、`LambProgrammer/dsh-desktop-zero` | 说明这条路**门槛不高、已有人走**，差异化必须来自别处 |
| 官方预留第三方载体接口：静态桌面页可提供 `__DSH_TRANSPORT__.streamBaseUrl`，原文档写 *"The desktop carrier owns authentication"* | **官方明确支持第三方承载** → 我们做载体是"被支持的正道" |
| DSH 插件 = TypeScript 模块（`apply(ctx)`），**无沙箱**，跑在 workspace sandbox 之外、进程内 | 强耦合路线的安全与维护成本高 → 不宜当主线 |

### 我们的差异化在哪（不是"再做一次套壳"）

- **形态**：别人给的是"窗口里的网页"；我们给的是**有立绘、有情绪、有记忆的角色**，DSH 会话嵌在这个角色里
- **本地能力**：桌宠已具备的能力（截图/OCR/剪贴板/日程/语音/好感度/回忆）正是纯 Web 端拿不到的东西
- **渐进**：载体走 HTTP 弱耦合（`127.0.0.1:3080`），DSH 升级不影响我们；插件路线需要跟着 TS API 变动走

## 四、多模型协作层：对他三个判断的回应

### 4.1 反向证据的再解读（他说得对）

我原来把"大厂都做单厂商多角色"当作反向证据，他的解读补上了动因层：

| 解释 | 是否成立 | 说明 |
|------|---------|------|
| 公司之间本身就不好合作，所以不做跨厂商 | **成立**（他给的解释） | 跨厂商协作对平台方 = 替对手优化 + 承担对方 API 的不确定性 |
| 商业化/成本考量 | 成立（我原来的猜测） | 自有权重才能做推理侧优化、成本可控 |
| 我们个人开发不需承担这些风险 | **成立** | 只做 provider 接口 + 协调层；钱和合规留在用户侧 |

**必须标注的边界**：以上三条是**判断与推演**，不是实证结论 —— 无公开一手材料证明大厂的取舍动因。
另有一条真实约束：若将来对外发布"多模型圆桌"，**多厂商 ToS（用你的 key 转发聚合）与费用转嫁**会成为现实问题 → 因此应把"谁付费、用谁的 key"留在**配置层**（LiteLLM / OpenRouter 这类网关正是这个抽象层）。

### 4.2 形态：不只群聊 —— 统一消息模型

他要的是"像 QQ/微信"：能私聊、能群里 @、能组织讨论。这要求**一套消息模型吃下三种拓扑**，而不是做三个功能。

| 拓扑 | 会话形态 | 投递语义 |
|------|---------|---------|
| 单聊 | `dm:human↔agent`、`dm:agent↔agent` | 定向投递（仅双方收件箱 + 人类可见） |
| 群聊 | `group:<id>` + 成员表 | 广播投递（全员收件箱） |
| 讨论/委派 | `thread:<id>`（挂在群或单聊下） | 定向 + 结果回投父会话 |

**推荐拓扑：共享追加日志（single source of truth）+ 每 agent 收件箱投影。**
理由：① 可见化天然成立（日志就是 UI 的数据源）② 私聊/群聊/线程统一 ③ 可回放、可审计、可算账（成本核算必须靠它）④ 投递语义集中在一处定义，不会三套逻辑打架。

### 4.3 ★ AI-AI 消息投递可见化：分层，而不是二选一

他问的是关键："在群聊里直接贴出来，还是单独列一个消息栏？" —— **两个都要，但分层，且同源。**

| 层 | 位置 | 放什么 | 默认 |
|----|------|--------|------|
| **L1 群聊流** | 群聊主窗口 | 人类要读的语义消息：谁说了什么、结论、请示、@人类 | 常显 |
| **L2 投递轨道** | 群聊右侧（或底部）**可折叠面板 / 独立"投递"标签页** | 结构化投递事件：`谁 → 谁`、类型、模型、耗时、token、成本、父子关系 | 折叠，一键展开 |
| **L3 后台总线** | 灰色/折叠区 | 心跳、重试、内部协调噪音 | 默认隐藏，仅调试 |

**为什么不全量贴进群聊流**：他的担忧是对的 —— AI 互聊会刷屏且烧钱；L1 只保留"面向人类的消息"，机器间的投递元数据进 L2，两边**读的是同一份日志**，不会出现两套数据不一致。

**建议的数据模型（每条消息一行）**

| 字段 | 说明 |
|------|------|
| `id` / `ts` | 单调递增 + 时间戳（回放/排序） |
| `channel_id` | 群 / 单聊 / 线程 |
| `sender` / `recipients` | `human:李滨宇`、`agent:pro`、`system`；收件人空 = 广播 |
| `kind` | `speak` 发言 / `ask` 提问 / `reply` 回答 / `delegate` 委派 / `arbitrate` 仲裁 / `tool` 工具调用 / `system` |
| `visibility` | `human`（进 L1）/ `meta`（只进 L2）/ `debug`（只进 L3） |
| `meta` | `model`、`tokens`、`cost`、`latency`、`parent_id`、`turn_no` |

**可见化的最小实现**：桌宠/壳里加一个"投递轨道"面板，用箭头渲 `sender → recipients`，颜色区分 kind，点击一条展开它的原文与成本 → 这一步**完全在本地做，不依赖 DSH**。

### 4.4 人类可打断 + 成本护栏（他点出的最重要一条）

| 机制 | 规则 |
|------|------|
| 人类插队 | 人类消息 `priority=highest`：**立即注入当前会话**，仲裁器在下一个回合边界**暂停自动轮转**，等人类"继续"**暂停后保持暂停并 @人类、不自动恢复**（"继续"必须是显式命令；原"超时 60s 默认恢复"口径已作废） |
| 回合上限 | 单议题最大回合数（建议默认 8） |
| 时长上限 | 单议题最长墙钟时间（建议默认 5 分钟） |
| 成本上限 | 单议题 token / 金额上限，触顶即停 |
| 收敛检测 | 连续 2 回合无新增信息 → 自动收束并输出结论 |
| 议题强制 | 群聊**必须**有议题 + 目标 + 结束条件才能开（禁止"无题自由群聊"） |
| 触顶行为 | 停 + 出结论 + `@人类`，绝不静默继续烧钱 |

| PySide6 | 6.11.1，含 `QtWebEngine*`、`QtWebView*` | 内嵌网页两条路都在；**但桌宠源码 grep 无 WebEngine 匹配** → 2.9.1 排除 WebEngine **不损任何现有功能** ✓ |
| Node.js | v22.22.0（来自 `C:\Program Files\AutoClaw\resources\node\`） | 可跑 JS 工具链；但**不是系统级安装**，路径绑 AutoClaw |

| Docker | ✗ 未装 | 容器化需先装 |
| gh | 便携版 `<便携目录>\gh.exe` ✓ | 不在 PATH |
| 磁盘可用 | C 146.7 / D 151.4 / E 134.6 GB | 充裕 ✓ |

### 明确"做不到"的事（不粉饰）

1. ✗ **本地跑圆桌不等于不花钱** —— 推理仍在云端 API，本地省的只是编排与 UI。
2. ✗ **本地跑 30B+ 级模型** —— 8 GB 显存不够；可行档位是 7B~8B Q4（能跑但速度一般）。
3. ✗ **现在就直接升 DSH** —— VM 不可达，需先确认其位置与启动方式。
4. ✗ **把无沙箱的 DSH 插件当主线** —— 安全面与维护面都不划算。
5. ✗ **同频跑"本地大模型 + DSH VM + 桌宠 + 浏览器"** —— 15.7 GB 内存会紧张。

### 需要准备什么

| 目标 | 前置动作 |
|------|---------|
| Tauri 哑窗口壳 | 装 Rust 工具链（约 1.5 GB + 首次编译耗时） |
| 纯系统 WebView 壳 | 无（WebView2 已装）→ 最小体积方案 |
| 内嵌 DSH 网页到桌宠 | 桌宠加 Qt6WebView（小）或 QtWebEngine（+195 MB）依赖 |
| 本地模型试跑 | 先定模型与量化（建议 7B~8B Q4） |
