01定位与三条铁律

归属负责什么
DSH模型与提供方配置、工具与技能、工作区、权限与审批、会话与轨迹、插件体系
桌宠立绘与情绪、语音（朗读/输入）、唤醒与提醒、本地能力（截图/OCR/剪贴板/日程/回忆）、协作层界面
适配层
dsh_adapter		唯一知道 DSH 细节的地方：端口、启动令牌、只读解析 settings.yaml
三条铁律 ① 单一事实来源 = DSH：模型/提供方/技能/工作区只有一份，桌宠只读镜像、不双写；
② .credentials.yaml 永不读取，密钥由用户自己在界面里填；
③ 不解析 DSH 的前端：只做宿主窗口 —— 它前端按插件动态装配、资源名带哈希（/plugins/??…&rev=<哈希>），碰它就是自找升级事故。

02目标与非目标

G1
一键把 DSH 当面板呈现，且它升级不破我家功能
G2
多模型/多角色协作：私聊 + 群聊 + @ + 组织讨论
G3
AI↔AI 投递可见、可算账、可打断
G4
桌宠自身能力完全独立可用

非目标（明确不做）：✗ 把 DSH 插件写进主干（会破坏性变更 + 插件无沙箱）；✗ 无议题的自由群聊（必然刷屏烧钱）；✗ 改 DSH 源码/提补丁（官方暂不接受外部 PR）；✗ 本地大模型当主力（显存 8,151 MiB 只够 7B~8B Q4）；✗ 承担商业化（个人自用定位，费用留在用户侧）。

04协作层设计

4.1 一套消息模型吃下三种拓扑

拓扑会话形态投递语义
单聊dm:human↔agent、dm:agent↔agent定向（双方收件箱 + 人类可见）
群聊group:<id> + 成员表广播（全员收件箱）
讨论 / 委派thread:<id>定向 + 结果回投父会话

字段：id/ts · channel_id · sender/recipients · kind（speak/ask/reply/delegate/arbitrate/tool/system）· visibility（human/meta/debug）· meta（model/tokens/cost/latency/parent_id/turn_no）。推荐拓扑：共享追加日志 + 每 agent 收件箱投影 —— 可见化天然成立、可回放、可算账、语义只定义一处。

4.2 投递可见化：三层，不二选一

层位置内容默认
L1 群聊流群聊主窗口人类要读的语义消息：谁说了什么、结论、请示、@人类常显
L2 投递轨道右侧可折叠面板 / 独立标签页谁→谁、类型、模型、耗时、token、成本、父子关系折叠
L3 后台总线灰色折叠区心跳、重试、内部协调噪音隐藏

不把投递全量贴进群聊流（刷屏 + 烧钱）；两层读的是同一份日志，所以不会出现两套数据。

4.3 人类可打断 + 成本护栏（默认值建议）

机制规则
人类插队最高优先级注入；仲裁器在下一回合边界暂停自动轮转，暂停后保持暂停并 @人类、不自动恢复（"继续"必须是显式命令）
回合上限单议题 8 回合
时长上限单议题 5 分钟
成本上限单议题 token / 金额上限，触顶即停
收敛检测连续 2 回合无新信息 → 自动收束出结论
议题强制无议题 + 目标 + 结束条件 → 不许开会
触顶行为停 + 出结论 + @人类，绝不静默烧钱

4.4 判断依据（诚实标注）

  • 事实：主流大厂产品全是单厂商多角色，没有跨厂商协作产品；唯一近似的 Bloome 查不到独立评测与活跃度。
  • 判断（非实证）：大厂不做跨厂商的动因是"自有权重才能做推理侧优化 + 成本可控 + 平台期动机"（你补充：公司间本就不好合作）。个人开发没有这层动机冲突 → "大厂不做"推不出"我们不该做"。
  • 约束：将来若对外发布，多厂商 ToS（用你的 key 转发聚合）与费用转嫁是真问题 → "谁付费、用谁的 key"留在配置层（LiteLLM / OpenRouter 这类网关正是该抽象层）。
  • 参考实现：AutoGen 的 GroupChat 仲裁策略、ChatDev 的"双人对话链"、AI Town 的对话可视化；不照搬 MetaGPT 的重 SOP。

4.5 "共用 API Key 省内存"是误解

设想能省本机内存吗真实影响
同厂商同一 key 多角色共用✗反而更早撞同账号 RPM/TPM 限流
同厂商多个 key✗扩容并发、隔离配额、便于分账（不省内存）
少接角色影响很小省的是 token 成本与墙上时间
本地跑模型（离线）✗ 反而大增这才吃显存（本机 8 GB → 7B~8B Q4）

05阶段路线与验收

P0（进行中）
DSH 本机化 + 载体最小闭环

验收：check-dsh.ps1 载体层绿；3080 HTTP 200；窗口可见。
已完成前半：本机安装 ✓ 启动器 ✓ 分层自检 ✓；载体窗口未做。

P1
消息日志 + 投递轨道（本地原型）

统一消息模型 + 三层视图 + 打断按钮，先用假数据。验收：日志可回放、成本可累加、打断后轮转确实暂停。

P2
多模型圆桌

provider 配置（复用 DSH 提供方）+ 仲裁器 + 四道上限。验收：2~3 角色 8 回合内收束、无题不启动、超限必停、人类插队生效。

P3（可选）
DSH 插件方向

TypeScript 插件接入 DSH 插件体系；只在 P0/P1 稳定后再评估。

06风险与对策

风险等级对策
DSH 破坏性变更打断我们中适配层唯一耦合点 + 能力探测/降级 + 升级后跑 check-dsh.ps1
官方不接受外部 PR—不能提交补丁让它兼容我们 → 只能自适配，适配层是必需项
官方桌面端成熟、载体失去价值中差异化押在"角色形态 + 本地能力 + 协作层"，不押在"能开窗口"
依赖未公开的 /api/*高不作依赖；要用先探测，失败即降级
多角色成本失控中四道上限 + 收敛检测 + 议题强制
本机算力不足中云端推理为主；本地只到 7B~8B Q4；编排层不占算力
双 harness 冲突高边界固化：DSH 管 agent 循环，桌宠管呈现与本地能力，记忆/权限各管各的

07版本策略

  • 基线：0.1.5-rc.2（npm latest）——已装 D:\dsh，服务 127.0.0.1:3080。
  • 可选升级：0.1.6-alpha.2（alpha）——含插件管理页、侧边栏 Subagent 会话、Office 预览；alpha 有回归风险。
  • 升级 SOP：装新版 → 跑 D:\dsh\check-dsh.ps1 → 看哪层断 → 只改对应一处（start-dsh.ps1 或适配层）。
