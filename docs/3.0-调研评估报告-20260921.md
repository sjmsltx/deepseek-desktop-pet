## 二、主线：与 DSH 高度耦合

### 2.1 查清的事实（官方仓库/文档原文）

| 问题 | 结论 |
|---|---|
| DSH 是什么 | DeepSeek 官方开源的 **agent harness**（运行时框架），不在只是 Web 控制台。仓库 `deepseek-ai/deepseek-harness`，描述原文 **"Everything is a Plugin"** |
| 许可/规模 | MIT；TypeScript 96.5%；**231,507★ / 27,762 fork**（2026-09-21 读数）；文档站 `deepseek-harness.github.io` |
| 成熟度 | README 原文 **"developer preview and iterating rapidly. THERE WILL BE COMPATIBILITY-BREAKING CHANGES."**；共 18 个 tag，用户装的 0.1.1-rc.2 已落后约 **5 个小版本**（最新 `dsh-v0.1.6-alpha.2`，2026-09-17） |
| 反馈渠道 | `has_issues: false`、`has_pull_requests: false` → **上游不收 issue/PR**，只走 Discussions |
| 插件形态 | 导出 `apply(ctx)` 的 **TypeScript 模块**（函数/对象/类三种）；由 Cordis 管生命周期与依赖注入（`inject = ['tools']`）；npm 分发，`dsh plugin --profile <name> add <spec>` |
| 扩展点 | 很多：`ctx.tools.register`、`ctx.skills`、`ctx.commands`、`ctx.settings`（含设置卡片）、`ctx.webServer.register*`、`ctx.clientModules`（浏览器端插件）、**`ctx.slots`（React 具名插槽）**、LLM adapter / subagent provider |
| **安全边界（重要）** | **插件没有沙箱**。官方原文：installed Host code executes in-process **outside the workspace sandbox**；权限系统只管"模型发起的工具调用" → 第三方插件 = 完全可信代码 |
| 前端 | React + Vite；API 是 Typert Gateway RPC（`/api` + `remote.mux` WebSocket）；鉴权 = 进程 token → 签名 Cookie（HttpOnly/SameSite=Strict，30 天） |
| **官方桌面端** | **官方已经自带 Electron 桌面端**（`apps/desktop`，默认端口 **19387**，仅发布 win-x64 / mac-arm64 / mac-x64，**Linux 不是受支持目标**） |
| **第三方桌面载体接口** | 官方明确预留：静态桌面页可提供 `__DSH_TRANSPORT__.streamBaseUrl`，并且原文 **"The desktop carrier owns authentication."** → 官方支持"第三方外壳承载 DSH"这条路线 |

### 2.2 关键判断

1. **"把网页端做成桌面形态"这件事，官方已经做了** ✗ → 我们再套一层 Electron 壳**没有增量价值**。
2. 我们真正的增量只有两块：
   - **本地能力桥接**：热键 / 麦克风 / 剪贴板 / 本地文件 / **COM 自动化（WPS/Office）** / 本地 MCP —— 这些是 Electron 壳拿不到的（Electron 做 COM 只能 spawn Python）；
   - **桌宠形态**：透明置顶立绘 + 常驻交互（DSH 官方桌面端是标准窗口应用）。
3. 因此主线更现实的形态是：**"桌宠（Python，含全部本地能力）作为 DSH 的桌面载体"**，通过官方 transport/carrier 接口接入，而不是"我们写一个 DSH 插件去做网页端"。
4. **风险清单**：developer preview + 破坏性变更 ✗（必须锁版本 + 做适配层隔离）、插件无沙箱 ✗（我方插件若分发，需要人工审核与最小权限）、上游不收 PR ✗（只能适配，不能提需求）。

### 2.3 可行性结论

**技术可行 ✓，但"高度耦合"（写 DSH 插件）成本高、回报低 ✗**；建议改为 **弱耦合载体优先**（见第五节路线）。已查到的坑：SSH 隧道场景下 DSH 的目录选择器失效（Discussions #3704，官方建议用 `host-directory-picker` 类方案）。

## 三、支线：圆桌（多模型协作）

### 3.1 市场（含竞品逐个拆）

| 产品 | 形态 | 协作机制 | 多厂商 | 证据强度 |
|---|---|---|---|---|
| **Bloome** (bloome.im) | 桌面+移动+网页 | AI agent 是群成员，可 @、可 thread、互相复核 | ✓ 明确 BYO 多厂商 | **弱**：只有官网自述 + 一个对比页；**未查到**独立评测/融资/用户量/仓库；官网高度 SEO 化 |
| Poe Multi-Bot Chat | 网页 | 同 chat 多 bot，互相可见 | ✗ 平台内 bot | 中（2024-04 发布，2026 状态未查到） |
| PolyBotChat (kleiber.me) | 网页实验 | 人类 + 多模型群聊 | ✓ | 弱，自述 experimental |
| Consensus（towardsai 文章） | 文 | OpenAI 兼容多 provider 结构化多方言说 | ✓ | 弱（无仓库/产品） |
| 大厂"AI 群聊"（ChatGPT 群组 / 元宝派 / 文心群聊 / UC） | 网页+App | 多角色 persona | **✗ 清一色单厂商** | 强（2025-11 ~ 2026-02 一波） |
| OpenWebUI / Cherry Studio / ChatHub / ChatALL / TeamAI | 网页/桌面 | **并排对比** | ✓ | 强 |

**判定标准（5 条，满足即时协作而非对比）**：共享时间线 / 互相可见 / 有发言权分配 / 收敛成一个融合结果 / 人类在时间线内。

**结论：真正"多厂商 API 在同一会话协作"的成品，只找到 Bloome 一家且证据弱 → 这个细分基本空白 ✓（用户直觉成立 ✓）**。但有一个**反向信号值得重视**：大厂一致选择"单厂商多角色"，而非"多厂商协作" —— 可能暗示后者在成本、体验一致性、责任归属上更难商业化。

### 3.2 学术（近两年，带 ID）

| 论文 | ID/时间 | 一句话结论 |
|---|---|---|
| AgentGroupChat-V2 | arXiv:2506.15451（2025-06） | 分治 + **异构 LLM 组合**；GSM8K 91.50%(+5.6pt)、AIME 近翻倍；**越难收益越大** |
| Why Do Multi-Agent LLM Systems Fail?（MAST） | arXiv:2503.13657（NeurIPS 2025） | 7 框架 1600+ traces → **失败率 41%–86.7%**，14 种失败模式 |
| Single-Agent LLMs Outperform MAS… | arXiv:2604.02460（2026-04） | **等 token 预算下**单 agent 信息效率更高 |
| Stop Overvaluing Multi-Agent Debate | arXiv:2502.08788（2025-02） | MAD 常打不过 CoT/自一致性，**但异构性是解药** |
| MultiAgentBench | arXiv:2503.01935（2025-03） | 协作/竞争基准；研究场景 graph 结构最好 |
| Who speaks next? | arXiv:2412.04937 | 引入人类会话的发言者选择机制，**显著减少对话崩溃** |

**唯一被反复验证的稳定增益点 = 异构模型**；其余收益都有争议，且必须做收敛/终止控制。

### 3.3 工程解法（可直接复用，不必自研）

- **回合仲裁**：规则驱动（轮转 + @ + 复核驳回），**不要用 LLM 当主持人**（CrewAI hierarchical 的教训）；Azure 官方 group chat orchestration pattern 建议 **≤3 个 agent**。
- **上下文**：摘要广播（只共享要点/结论/失败/约束），共享全文 token 成本非线性爆炸。
- **收敛**：Azure 把"管理者无法客观判定完成"列为该模式的**避免使用理由**之一 → 必须硬性 round cap + 收尾动作。
- **多 provider / 多 key 成本与权限**：用 **LiteLLM**（MIT，自托管，virtual key 级花费追踪 + 预算实时执行 + SSO/RBAC），**不要自研**。

## 四、技术底座：桌面壳选型（承载网页）

### 4.1 本机实测基线

| 项 | 实测 |
|---|---|
| 现有桌宠发布包 | **152 MB**（dist） |
| Qt WebEngine 必需件 | **210.8 MB**（单 `Qt6WebEngineCore.dll` 就 195.3 MB）；另 locales 43.8 MB、`*.debug.pak` 74.5 MB |
| WebView2 Runtime | **已装** 153.0.4234.48（Win11 自带；Win10 缺则 ~2 MB bootstrapper） |
| Rust/Go 工具链 | **未装**（Tauri/Wails 需要先装） |

### 4.2 对比表

| 方案 | Win 上体积 | 需否预装 | 原生桥（热键/COM/托盘） | 备注 |
|---|---|---|---|---|
| **pywebview**（WebView2） | **+0.5 MB** | 需 WebView2（已装） | 弱（需自己补 Win32） | **不支持 Windows 透明窗** ✗ |
| **Tauri v2** | 壳 3–10 MB | 需 WebView2（已装） | 官方插件齐（global-shortcut/clipboard/tray/single-instance） | 需装 Rust；远程 URL 需配 capability |
| **Electron** | +150 MB 运行时 | 否 | 最全 | 双运行时，收益低 → **不选** |
| **PySide6 + QWebEngineView** | **+211 MB**（总约 360 MB） | 否 | 进程内，现有 Python 能力**原样可用** ✓ | 体积代价大 ✗ |
| Neutralino / PWA(Edge --app) | 极小 | 需系统 webview | 无/受限 | 兜底 |

### 4.3 结论

- **桌宠保持 Python 不动**（透明立绘窗口用 PySide6 ✓，pywebview **做不到透明** ✗）。
- Web 控制台用一个**"哑窗口"壳**承载，**本地能力仍由 Python 通过本地 HTTP/MCP 提供** —— 壳零桥接，避免新增 IPC 复杂度 ✓。
- 首选 **pywebview**（0.5 MB + WebView2 已装 ✓）；若要托盘/热键/单实例/更新等完整壳能力 → **Tauri v2**（需装 Rust）；坚持纯现栈 → PySide6+QWebEngineView，代价 **+211 MB**。
- 过渡方案：先用 `msedge --app=http://127.0.0.1:3080`（0 成本，非公开承诺 API）。

## 五、建议路线（分期，不拍不做）

| 期 | 内容 | 为什么这个顺序 |
|---|---|---|
| **P1**（低风险，先摘果子） | 桌宠 + **哑窗口壳**承载 DSH Web UI（pywebview 或 Edge --app），本地能力经本地 HTTP/MCP 单向暴露给 DSH 会话 | 不动 2.x 架构；立刻可用；验证"桌面载体"这条路是否真有价值 |
| **P2** | 按官方 carrier/transport 接口做**正式桌面载体**（`__DSH_TRANSPORT__`），并考虑把一个"本地能力插件"用 TS 写（跟随官方插件 API，锁版本） | 官方 API 处在 developer preview，放在第二步，避免白干 |
| **P3** | 圆桌 MVP：**上限 3 个角色**（起草/挑刺/收敛）+ 规则制回合 + 人类可打断 + 摘要广播 + 硬 round cap + LiteLLM 管多 provider 额度 | 这条线是"可能比桌宠更有产品感"的方向，但**先用自有任务集跑 baseline（单强模型 + CoT/自一致性）验证增益**，再决定投入 |

**明确不做（现阶段）**：不做并排对比（已饱和）、不做 N-agent 通用编排、不做 LLM 当主持人、不做自主无限互聊（刷钱机器）、不做企业级审计/SOC2。
