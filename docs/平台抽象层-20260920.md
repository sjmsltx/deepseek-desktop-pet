# 平台抽象层（P1）· 2026-09-20

> 批次 1 交付物。**先做转发、后做收编**：本批只新增 `platform_layer.py` 一个文件，
> **不动任何既有文件**（对方 Batch 3 仍在制品，避免互相踩）。
> 调研方式是"实测定位现状"，不是先画接口再找地方用。

## 1. 为什么要做

现在与操作系统耦合的能力**散在 4 个模块 + 宿主内联代码**里，调用方（`desktop_pet.py`、设置窗、
技能包、小游戏）直接 import 具体模块，或直接写 `ctypes.windll.user32.*`。后果：

- **跨平台无从下手**：想支持 macOS/Linux 得改调用方 n 处；
- **能力不可见**：界面上无法回答"这台机器到底能不能朗读/OCR/全局热键"；
- **重复建设风险**：每加一个入口就多一份 Win32 调用（热键注册就同时出现在两个地方）。

## 4. 三条硬约定

1. **导入期不 import 平台专有模块**（`winreg` / `winsound` / `ctypes.windll`）—— 一律函数内延迟 import。
   否则非 Windows 上 `import platform_layer` 直接炸，跨平台免谈。
   （`tests/test_platform_layer.py` 用**独立子进程**验证：`import platform_layer` 后
   `sys.modules` 里**没有** `winreg` / `winsound` / `PySide6`。）
2. **能力缺失不抛异常**，返回降级值（`False` / `''` / `0`），由 `capabilities()` 如实报告。
3. **未收编项转发宿主**，不另写实现 —— 避免两套实现打架。

## 6. 不做 / 风险

- **不做**：把 Qt 全换成跨平台抽象（界面已跨平台）、把 COM 办公能力抽象（Windows 专有，诚实报不可用即可）。
- **风险**：收编时容易顺手"改进"自启实现 → 已在第 2 节钉住方案，迁移时对照验收（开/关后 `启动` 文件夹状态、历史 Run 项不再出现）。
- **验收标准**：① 批次 1 不修改任何既有文件；② 全量测试通过；③ 非 Windows 降级不抛异常；
  ④ `report()` 能如实反映"哪些能、哪些不能、经谁实现"。
