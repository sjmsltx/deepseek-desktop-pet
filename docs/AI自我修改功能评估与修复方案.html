AI 自我修改功能 · 拆分后评估与修复方案

edit_own_code / read_file / install_plugin 在 14 模块架构下的问题盘点、可行性检查、修复路径（2026-08-31）

一、现状问题盘点（拆分放大的硬伤）

问题现状严重度
edit_own_code 硬编码单文件handler 里 `path = BASE_DIR/desktop_pet.py` 写死——拆分后 AI 无法修改其他 13 个模块，要求改 affection_engine.py 也会被改到 desktop_pet.py高（功能失效）
AI 不知道项目结构提示词只有「read_file 相对 desktop-pet-dev」——目录名都过时了，且没有模块清单/职责说明，AI 只能猜路径高（找错位置根源）
无代码搜索能力AI 想找「好感度在哪实现」——只能 read_file 逐文件猜，没有 grep 工具。人类靠 Ctrl+Shift+F，AI 没有高（找错位置根源）
read_file 不能浏览目录传目录返回「不支持读取该类型文件」，AI 无法列出项目文件中
行号编辑依赖先读对文件按行编辑要求先 read_file 带行号——文件猜错了，行号全错，改错位置高
用户反馈「找会找错位置，不尽人意」的根因：AI 只有「猜路径读文件」一种定位手段，没有「地图（结构清单）+ 搜索（grep）+ 浏览（目录列表）」。单文件时代勉强能用，14 模块后必然迷路。

二、不受拆分影响的部分（无需改）

能力说明
git 保护edit_own_code 改前提交基线 + 语法验证 + 失败不落盘 + backup 双保险——逻辑与文件数无关，扩展 file 参数即可复用
插件系统install_plugin 写入 plugins/ 独立目录 + 热加载，不碰源码——不受拆分影响
主题系统set_theme / theme 插件独立于源码——不受影响
write_config白名单字段 + 热加载——独立功能
write_file输出文件写 输出/ 目录——与源码隔离，安全

三、可行性检查（修复方案）

① 项目模块地图注入 system prompt 低风险 · 高收益

system prompt 加「项目结构」段：列出 14 个模块文件 + 职责一句话（如 affection_engine.py=好感度引擎、memory_store.py=记忆数据层）。AI 第一次就知道去哪找。

② read_file 支持目录浏览 低风险 · 10 行代码

rel_path 是目录时返回「文件名 + 行数 + 一句话职责（内置映射）」列表——AI 可探索。

③ 新增 search_code 工具（grep） 中低风险 · 根治找错位置

新工具：关键词 → 扫描所有 .py 模块，返回「文件:行号:代码行」命中列表（限项目目录、限 .py、限 20 条）。AI 找功能 = 搜索而非猜路径。

④ edit_own_code 支持多文件 中风险 · 核心修复

加 file 参数（默认 desktop_pet.py）：白名单限定 .py 模块（排除 tools_registry.py 等生成文件？不——全部允许，git 保护兜底）。行号/old_text 编辑逻辑复用，git 基线 + 语法验证 + backup 扩展到目标文件。

⑤ 提示词更新（9 条规则 5/7 条 + 工具 description） 低风险

「desktop-pet-dev」→ 实际目录名；「只改 desktop_pet.py」→ 「可改任意模块，优先 search_code 定位」；read_file/edit_own_code 的 description 同步更新。

四、风险评估

风险现有防线补充
AI 乱改代码破坏功能git 基线提交 + 语法验证 + 失败不落盘 + backup 双保险改前自动备份到 backup/（已有）；改后提示用户重启验证
AI 改错模块—（当前无）search_code 定位 + 模块地图 + file 参数白名单
search_code 泄露敏感信息—只搜 .py 源码（排除 config.json 等数据文件）；config.json 等本来就不在搜索范围
grep 性能—14 个模块总 ~1.6 万行，秒级完成；限制结果 20 条

步骤内容预计

结论：可行且必要。核心是给 AI「地图（模块清单）+ 搜索（grep）+ 浏览（目录）」三件套，把定位方式从「猜」变成「查」。git 保护体系现成，多文件化风险可控。总工作量约 1.5 小时。
