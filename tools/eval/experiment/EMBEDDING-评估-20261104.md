# Embedding 可行性评估（2026-11-04）

> 生成时间：2026-11-04 15:35
> 触发：Owner「embedding评估一下」
> 结论先行：**技术上可行、收益明确（精度 65%→85%，语义召回 12%→95%），
> 代价是包体积 +65MB（+29%）和一条新依赖。是否做需 Owner 拍。**

## 一、先确认一个前提：DeepSeek 没有 embedding 接口

查官方文档（不是社区 issue）：

- `https://api-docs.deepseek.com/` 只列 **对话(Chat) / 补全(Completions) / 模型(Model)**
- `/models` 返回的只有 `deepseek-v4-flash` / `deepseek-v4-pro`
- 侧边栏无 embeddings / 向量 条目

⇒ **「复用现有 key 做语义」这条路不通。** 只能走本地模型（或再签一家厂商的 key）。

⚠ 网上有 issue 说 DeepSeek「暴露了 OpenAI 兼容 embeddings」，那是社区误传
（`text-embedding-v3` 是别家的模型名）。**以官方文档为准。**

---

## 二、评估方法（不靠主观挑例子）

| 实验 | 做法 | 量什么 |
|---|---|---|
| ① 同义改写召回 | 让模型把 40 条真实记忆**保留含义换用词**改写，再看算法认不认这 40 对 | 漏连率 |
| ② 现有强边精度 | 从真实强边抽 80 条，让模型判定「两段记忆是否真相关」 | 误连率 |
| ③ 真机实测向量 | 下载 `bge-small-zh-v1.5` int8 ONNX（22.9MB）本地跑，同一批数据对比 | 收益是否兑现 |

改写分两档：
- **变体 A**：允许保留专有名词（同一件事被自然复述的真实情形）
- **变体 B**：连专名也换成描述（「合川桃片」→「那种薄薄的甜味切片」）＝纯语义改写

脚本：`scripts/eval_embedding.py`（① ②）、`scripts/probe_embedding_local.py`（③）
数据：`results/embedding-eval.json`

## 三、结果

### 3.1 词面边的两个缺陷（实测）

| 指标 | 数值 |
|---|---|
| 同义改写召回（变体 A，允许保留专名） | **78%**（31/40）⇒ 漏 22% |
| 同义改写召回（变体 B，纯语义改写） | **18%**（7/40）⇒ **漏 82%** |
| 现有强边 precision | **65%**（52/80）⇒ **1/3 是误连** |

变体 B 的 jaccard 中位只有 **0.0132**（阈值 0.045）—— 语义相同但字面几乎不重叠。

> 波动说明（2026-11-04 重跑）：改写用 temp=0.9，重跑会漂。三次观测 A 78~80%、B 12~18%。
> 定性结论（B 档词面几乎抓不住）稳定；具体小数请连同样本量一起引用。
> ⚠ 当时那份 `results/embedding-eval.json` 曾被一个「以为 kill 掉了其实没死」的
> 早期失败运行覆盖成 A 42.5%/B 0%(8 条)，已重跑修正，旧件备份在
> `桌宠记忆实验-20261103/embedding-eval.CLOBBERED.json`。

### 3.2 误连长什么样（都是「同一模板句」）

80 条抽样里 28 条被判不相关，典型：

| 词面 jaccard | 向量 cosine | 两条记忆 | 为什么会连上 |
|---|---|---|---|
| 0.085 | 0.501 | 拿铁「慢慢调整喝法」 / WPS「细节上还在慢慢调整」 | 共享「慢慢调整」 |
| 0.513 档 | 0.513 | 聊「鱼香肉丝」 / 聊「练打字」 | 共享「前两天跟同事聊过…同事说」 |
| 0.119 | 0.523 | 「遥感图像解译…每周抽时间看几幅图」 / 「读《定风波》…每周都会读一遍」 | 共享「每周都」 |

**这不是巧合**：2-gram 把「句式」当成了「内容」。模板句一多，误连就多。

### 3.3 向量能不能救

**改写召回（变体 B）**

| 判据 | 认出 | 说明 |
|---|---|---|
| 词面 jaccard ≥ 0.045 | 18% | 现况（三次运行 12~18%） |
| 向量 cosine ≥ 0.60 | **95%** | 中位 0.724 |
| 向量 cosine ≥ 0.65 | 82% | |
| 向量 cosine ≥ 0.70 | 70% | |

**强边精度**（同一批 80 对，LLM 判定为基准）

| 阈值 | 保留真相关 | 剔除误连 | precision |
|---|---|---|---|
| 现况（无向量） | — | 0% | 65% |
| 0.55 | 98% | 29% | 72% |
| **0.60** | **87%** | **71%** | **85%** |
| 0.65 | 65% | 89% | 92% |
| 0.70 | 40% | 100% | 100% |

相关对 cosine 中位 0.688（最低 0.532）／不相关对中位 0.571（最高 0.675）
⇒ 两类有**重叠区**（0.53~0.68），阈值注定要取舍，做不到两头都满。

### 3.4 一句话结论

**embedding 同时改善精度和语义召回** —— 这正是词面度的死结：
它把「句式相同」当相关（假阳），又把「换了说法」当无关（假阴）。

## 四、代价（工程口径）

| 项 | 数值 | 备注 |
|---|---|---|
| 模型 | **22.90 MB** | `Xenova/bge-small-zh-v1.5` int8 ONNX，512 维，中文专用 |
| tokenizer | 0.42 MB | `tokenizer.json`；若手写 WordPiece 只要 `vocab.txt` 0.10MB |
| 新依赖 | **+41.9 MB** | `onnxruntime`（当前环境已装，但**不在 requirements.txt**） |
| 合计体积 | **约 +65 MB** | 现有 release asset 223.7MB ⇒ 约 289MB（**+29%**） |
| 速度 | **2.64 ms/条** | batch=64、128 token、CPU |
| 全量编码 | 1417 条 3.75s／5000 条 13.2s／50000 条 132s | 一次性，可缓存 |
| 向量存储 | 512×float32＝2KB/条 | 1417→2.9MB；50000→100MB（int8 压到 512B/条 ⇒ 0.7MB / 25MB） |
| 许可 | **MIT**（基座 `BAAI/bge-small-zh-v1.5`） | Xenova 是其 ONNX 转换版 |
| 离线 | 模型需**随包发布**（首次运行不许联网下载） | 否则断网即降级 |

### 环境事实（本机实测）

```
Python 3.14.3
  numpy 2.4.6 ✓   onnxruntime 1.27.0 ✓   tokenizers 0.22.2 ✓
  transformers 5.13.1 ✓（98MB，不必随包）   sklearn 1.9.0 ✓
  torch 2.13.0+cpu ✓（496.6MB —— **绝不能随包**）
```

⇒ 走 ONNX 路线（22.9MB），**不走 torch**（496MB，会让发行包翻 3 倍）。

## 五、三种可选口径

| 方案 | 边怎么定 | precision | 语义召回 | 代价 |
|---|---|---|---|---|
| **A 现状（纯词面）** | jaccard ≥ 0.045 | 65% | 12%（纯语义） | 0 |
| **B 向量替代** | cosine ≥ 0.60 | **85%** | **95%** | +65MB，需缓存与回退 |
| **C 词面 OR 向量** | 任一命中 | 65%（不降不升） | ≈100% | 同上，但**误连一条不少** |
| **D 词面 AND 向量** | 两者都要 | 高 | 低 | 同上，线会变少很多 |

**C 的真相**：OR 只能补漏，不能去噪（现有 1/3 误连原样保留）。
**D 的真相**：AND 会砍掉大量真相关（词面本来就只有 65% 准）。

⇒ 若做，**取 B**（向量为主判据 + 词面兜底），阈值 **0.60**。

## 六、我的建议

### 建议做，但**不为「星图的线」单独做**

理由：单为连线引入 65MB 换来「线更准」，投入产出不划算 ——
线只是观感。**真正的收益在检索闸门**：

桌面宠物线已实测「词面检索的留出集 R@3 天花板 42%，
把闸门全关也只有 42%，因为字面匹配打不过同义改写」
（`memory_engine.py` 闸门注释里的原话，本轮实验再次确认变体 B 只有 12% 召回）。

**同一份模型、同一份向量缓存，可以同时服务两件事**：
1. 星图的边（精度 65%→85%）
2. 检索闸门 / 召回（这条没测，但方向一致，需另做实验验证）

⇒ 若做，按「一个 embedding 组件，两个消费方」立项，而不是「给星图加个线算法」。

### 若做，必须带的三条工程约束

1. **可选组件 + 优雅降级**：模型缺失/加载失败 ⇒ 自动回退纯词面，功能不消失
   （产品已有先例：Live2D 缺失时降级并记原因）
2. **增量编码 + 持久化**：只给新记忆算（2.64ms/条），向量存旁文件；
   模型或参数变了要能检测并重算（否则新旧向量不同空间、cosine 无意义）
3. **阈值要能校准**：本轮这套评测脚本留着，改模型/阈值后重跑一遍再上线

### 什么情况下我会改口说「别做」

- 若 Owner 认为 **+29% 包体积**不可接受 → 不做（这是唯一硬约束）
- 若只想要「线更准」而不碰检索 → 收益太小，不做
- 若要求「一条命令离线可复现、不许首次联网」而模型不能随包 → 不做

## 七、未验证 / 风险（别当结论用）

| 项 | 状态 |
|---|---|
| embedding 对**检索闸门**的收益 | **未测**。方向一致但需单独实验（用 `cases.json` + `negatives.json` 跑 R@3/误注入） |
| 量化模型的跨版本一致性 | 未测。onnxruntime 版本升级后向量可能微变 ⇒ 需钉版本 + 缓存版本号 |
| 50000 条时的冷启动 | 132s，必须后台 + 进度提示；本轮未做 |
| 边抽样的偏差 | ⚠ 80 条**从现有词面边里抽**，所以「词面召回」在该集合上是 100%（构造使然），**只有 precision 有意义**。语义召回用独立的改写对测 |
| LLM 判定的主观性 | 判定用 `deepseek-flash` 单次、从宽口径；换 prompt 或换模型，precision 的绝对值会浮动。趋势可信，绝对值别精确引用 |

## 九、本轮踩的两个坑（都记进脚本注释）

1. **`response_format=json_object` 要求提示词里出现 "json" 字样**，否则 DeepSeek 返回 400
   ⇒ 改写的 40 次调用全失败（0/40），看着像"模型不行"其实是调用写错。
2. **`thinking` 必须显式关掉**。deepseek-flash 是推理模型，`reasoning_tokens`
   **计入** max_tokens：实测 260 / 2000 预算都能被思考吃光、`finish_reason=length`、
   `content` 为空。改写/判定这类任务加 `'thinking': {'type': 'disabled'}` 后正常
   （2.64ms 的本地编码也才是纯算力）。
