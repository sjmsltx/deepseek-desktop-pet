## 一、为什么用 batch 当真值，以及它为什么不够

`memories-1411.json` 的 `batch` 字段是按种子对话分批的（239 批，每批 3~9 条）：

```
batch 0   遥感原理课程：偏好 / 态度变化 / 整理笔记习惯 / 公式卡点 / 学长建议
batch 57  鱼香肉丝：  偏好 / 固定讲究 / 长期习惯 / 口味变化 / 与人聊起
```

这正是 Owner 说的「一件事的多个方面」。但它**只是「一段对话的主题」，不是实体**。
实测反例：

| 组 | 余弦 | 实际关系 |
|---|---|---|
| batch 86（VS Code） vs 87（PyCharm） | 0.953 | **不同工具** |
| batch 79（睡眠不好） vs 60（凌晨才睡） | 0.951 | **同一件事被拆开** |

⇒ 用 batch 当真值，两个方向都有偏：同实体被拆开（低估召回）、同主题不同对象被算错（高估混淆）。
所以下面的数只能当**参考**，真正的结论靠 §三 那组机械判据。

## 二、可分性（局部指标）

| 指标 | 结果 |
|---|---|
| 同 batch 对（3581 组）中位余弦 | 0.6845 |
| 跨 batch 对（991174 组）中位余弦 | 0.5025 |
| 中位差 | 0.1820 |
| 分布 | **有重叠**（同实体 p10 0.578 < 异类 p90 0.597）|
| **最近邻含同实体（top-1）** | **54.4%** |
| top-3 含同实体 | 73.6% |
| top-5 含同实体 | 78.7% |

**最近邻只有 54% 同实体** —— 一半以上的「最近邻」其实是别的事。
这是不受类别不平衡影响的局部指标，比 pairwise F1 更能说明问题。

同一个 batch 内部（同一件事的不同面向）：min 中位 0.585 / 中位 0.684 / max 中位 0.784。
而跨对象的最高相似度能到 0.95 —— **两个区间完全重叠**。

## 三、决定性证据：高相似到底来自哪里

对相似度 ≥0.85 的 71 组做机械判读（用拉丁专名是否交集判断「是否同一具体对象」，
不靠我人工判读）：

| 类别 | 数量 | 占比 |
|---|---|---|
| **不同具体对象**（都有拉丁词且无交集） | **41** | **58%** |
| 可能是同一对象（拉丁词有交集） | 1 | 1% |
| 判不了（至少一方无拉丁词） | 29 | 41% |

样例（全部是「不同工具」，却被判为高度相似）：

| 余弦 | 一对 | 原文 |
|---|---|---|
| 0.866 | ArcGIS Pro vs MATLAB | 「长期使用 ArcGIS Pro…习惯已保持好几年」/「从本科开始用 MATLAB…好多年」 |
| 0.873 | ArcGIS Pro vs VS Code | 「长期使用 ArcGIS Pro…好几年」/「写代码到现在基本一直用 VS Code…好几年」 |
| 0.867 | ArcGIS Pro vs WPS | 「长期使用 ArcGIS Pro…好几年」/「用 WPS 已经好多年…」 |
| 0.850 | QGIS vs Blender | 「喜欢 QGIS，开源免费、插件多」/「在 3D 软件上更偏爱 Blender，插件也多」 |
| 0.855 | ENVI vs MATLAB | 「用 ENVI 差不多三年…」/「用 MATLAB…好多年」 |

**看清楚这些句子**：它们句式几乎一模一样（「长期使用 X，习惯保持好几年」）。
所以 0.86 的相似度是**模板相似**，不是对象相同。

⇒ 这和之前 Jaccard 的问题**同源**：算法抓住了「句式」，没抓住「说的是哪件事」。
换成 embedding 没解决，只是换了个抓手。

## 四、聚类与压缩（参考数，受真值偏差影响）

层次聚类（average linkage，余弦距离）：

| 距离阈 | 簇数 | purity | 实体召回 | 中位簇内 batch 数 |
|---|---|---|---|---|
| 0.200 | 1223 | 0.936 | 0.050 | 1.0 |
| 0.250 | 896 | 0.849 | 0.255 | 1.0 |
| 0.300 | 576 | 0.758 | 0.502 | 1.0 |
| 0.325 | 427 | 0.701 | 0.653 | 1.0 |
| 0.350 | 321 | 0.616 | 0.707 | 1.0 |
| 0.400 | 161 | 0.410 | 0.837 | 2.0 |
| 0.450 | 57 | 0.172 | 0.929 | 3.0 |

取簇数接近真值的一档（阈 0.300）：**576 簇 / purity 0.758 / 实体召回 0.502**。

- purity 0.758 ⇒ 每个簇里最多的那个实体只占 76%，其余是混进来的
- 压缩比只有 **2.4 : 1**（1411 → 576），不是「压成 239」
- 单条簇 242 个（42%）—— 四成条目根本没被归并

**「把所有条目并成 1 簇」时 purity 0.009、实体召回 1.000** ——
这说明 purity 与实体召回是反向的，任何单点都在做取舍，没有免费的方向。

## 五、聚合的信息代价

策略：每簇成员按 importance 降序拼，预算 200 字。

| 项 | 结果 |
|---|---|
| 原始记忆的 2-gram 在聚合句里的留存率 | 中位 **1.00** / 均值 0.96 / <0.5 的占 5% |
| 解读 | 因为簇小（中位 2 条）、预算 200 字够用 ⇒ **这不是压缩，是拼接** |

⇒ **拼接式聚合没有压缩效果**。真要压缩（一条覆盖多个面向且更短），
只能让 LLM 重写，那会丢内容（`实验文稿-记忆检索与结构化` §3.1：纯语义改写后词面 jaccard 中位 0.0132）。

## 七、结论（对产品设计的影响）

| 判据 | 数据 | 含义 |
|---|---|---|
| 最近邻同实体率 | 54.4% | 向量抓不住「同一件事」 |
| 高相似对里不同对象占比 | 58% | 高相似主要来自**句式模板** |
| 实体召回 / purity | 0.502 / 0.758 | 聚类两头都不合格 |
| 压缩比 | 2.4:1 | 收益很小 |

**⇒ 不要用「事后向量聚类」来做多维节点。** 这条路的数据不支持。

### 应该怎么做（这是本次原型的真正产出）

1. **实体键必须在抽取阶段显式产出**
   LLM 抽取时同时输出 `entity`（这是哪件事：如「编辑器偏好」「睡眠习惯」），
   而不是事后从文本算相似度。模型知道「VS Code ≠ PyCharm」，
   余弦不知道 —— 因为两者的句子模板一样。

2. **面向（aspect）由抽取侧分类，不由聚类发现**
   同一实体的面向（偏好/习惯/变化/卡点/他人建议）是**有限且可枚举**的，
   可以直接定义成枚举值，比无监督发现可靠。

3. **聚合摘要必须 LLM 写，且要保留「可回溯原句」**
   拼接无压缩效果，重写会丢措辞 ⇒ 聚合只是**注入视图**，
   原节点仍要留着（这与已经落地的「只改 status 不物理删除」一致）。

4. **这仍然是改数据结构**（加 `entity` / `aspect` 字段 + 迁移 44 条 + 改抽取 prompt），
   不是加参数。下一步应该先做**抽取侧可行性验证**：
   给定 1411 条，让 LLM 只做「实体键 + 面向」标注，测标注一致性与成本，
   再谈是否动产品。

## 八、本轮我犯的三个错（都是同一个形状：先有结论再找数）

1. **选阈值的选择函数坏了**：`f1*0.6 + 实体召回*0.4` 会在「全并成 1 簇」时给出最高分
   （实体召回天然 1.0）⇒ 选中 19 簇、最大簇 921 条的塌缩结果，
   还据此报出「压缩 74:1」「注入率 87%→16%」。
2. **在塌缩结果上算的数照发**：那些数字全部作废（v2 已重算）。
3. **手写结论与数字相反**：留存率实测 6%，我印「大约只保留了原句一半的措辞」。

v2 的改法：选阈值加「簇数必须在真值 [0.5x, 3x] 内」的硬约束；改用局部指标（kNN）；
结论句全部由变量插值生成。
