## 摘要

本文记录一次完整的「记忆系统能不能长大」的技术验证，五组实验串成一条线：
**词面检索的上限在哪 → 语义检索能不能突破 → 阈值稳不稳 → 淘汰能不能按权重 → 记忆节点能不能多维度**。

主要结论四条：

1. **语义检索能突破词面天花板**：留出集 R@3 从 3/12（25%）升到 11/12（92%），越过「闸门全关也只有 5/12（42%）」的硬顶。代价是 +65MB 体积与一个必须同时上线的守卫。
2. **固定阈值随库增长会失效**，机制是极值效应：区分度从 0.107（21 条）塌到 0.022（1432 条）。这是绝对判据的结构性缺陷，调参修不了。
3. **按权重淘汰确实改变了结果**：3/3 对 0/3（同样三条记忆，按权重全存活，按时间全淘汰）。
4. **用向量聚类做「一个节点=一件事」不可行**（负结果）；**把实体判定挪到抽取侧可行**：给 `topic + object` 两维后判别冲突 0 组、归并召回 0.868，均优于余弦聚类（0.758/0.502）。

最大的意外：词面检索与向量检索**失败在同一个地方** —— 它们抓的都是**句式模板**，不是「说的是哪件事」。

## 1 背景

### 1.1 触发问题的三件事

**① 记忆检索的硬顶。** `memory_engine.py` 里有一句自己写的判词：

> 把闸门全关（matched=0、cov=0），留出集也只有 42%。字面匹配打不过同义改写
> （「我大几」vs「用户是大二学生」无共同 2-gram）。要往上走必须加同义词表或语义检索。

**② 容量上限与「成长」的设想。** Owner（2026-11-04）：

> 记忆你给他设置一个 200 条上限……用一年两年十几年二十几年那就会出大问题。
> 我觉得不仅仅这个上限它可以成长……那个记忆本身也可以成长，也不一定非要每一个节点
> 只有一条事情，每一个节点都可以是一个多维度的。

**③ 校准现状时发现的两个事实**（先纠错，再实验）：

| 库 | 上限 | 淘汰判据 | 现状 |
|---|---|---|---|
| `memory.json`（事实层 facts） | **无** | **无** | 44 条（21 active） |
| `memories.json`（事件层 events） | `MAX_MEMORIES=200` | 纯按插入顺序 | 6 条 |

即：「200 条上限」从来只作用于事件层；事实层是**裸增长**（唯一写入点 `append` 后无任何容量判断）。
另外实测 2 万条检索只要 5.42ms ⇒ **容量在性能上不是瓶颈，成本全在注入噪声**。

## 3 结果

### 3.1 实验一：词面到底差多少

**同义改写召回**（40 对，`STRONG_EDGE_JACCARD=0.045` 为判据）：

| 变体 | 词面认出 | 漏连 |
|---|---|---|
| A 允许保留专名 | **78%**（31/40） | 22% |
| B 连专名也换成描述 | **18%**（7/40） | **82%** |

B 变体的 jaccard 中位 **0.0132**、最大 0.0645 —— 语义相同而字面几乎不重叠。

> 波动说明：同义改写用 temp=0.9，重跑会漂。观察到 A 78%~80%、B 12%~18%（三次运行）。
> 结论「B 档词面几乎抓不住」稳定，具体小数请附样本量引用。

**现有词面强边的精度**（80 对，模型判定）：**65%**（52/80），即约 1/3 是误连。

误连的成因一致 —— 同一模板句：

| 词面 | 两条记忆 |
|---|---|
| 共享「慢慢调整」 | 拿铁「慢慢调整**喝法**」/ WPS「细节上还在**慢慢调整**」 |
| 共享「每周都」 | 「遥感…**每周**抽时间看几幅图」/「读《定风波》…**每周**都会读一遍」 |
| 共享「前两天跟同事聊过」 | 聊鱼香肉丝 / 聊练打字 |

**向量能否救**（int8 真机）：纯语义改写召回到 **95%**（cos ≥0.60）；强边 precision 到 **85%**（同阈值）。

### 3.2 实验二：阈值与稳健性

**召回**（留出集 12 条）：

| 口径 | holdR@3 | 95% Wilson CI |
|---|---|---|
| BM25 现况（cov 0.30） | 3/12 = 25% | [9%, 53%] |
| BM25 闸门全关 | 5/12 = 42% | — |
| 向量 cos ≥0.51 | **11/12 = 92%** | **[65%, 99%]** |
| 向量 cos ≥0.60 | 5/12 = 42% | — |

两区间不重叠 ⇒ 差异显著；但 12 条只能支撑「大概率 65%~99%」，不能当精确值。

**稳健带**（按真实 R@3 扫 0.005）：

| 阈值 | holdR@3 | 注入率 |
|---|---|---|
| 0.435 | 12/12 | 76% |
| **0.440 ~ 0.515** | **11/12** | 73% → **36%** |
| 0.510（采用） | 11/12 | 36% |
| 0.520 | 10/12 | 31% |
| 0.545 | 8/12 | 24% |
| 0.600 | 5/12 | 18% |

当前 0.51 距上沿仅 **0.005**；越界后果温和（0.52 → 10/12），危险方向是**向下**（0.44 → 注入 73%）。

**换量化还成不成立**（int8 22.9MB vs fp32 90.5MB，同一批 12 条）：

| 项 | 结果 |
|---|---|
| top1 命中对象是否相同 | **12/12 相同** |
| 逐条余弦差（fp32−int8） | 中位 **−0.0099**，范围 −0.0277 ~ −0.0029，12 条全负 |

⇒ 语义排序稳，但**余弦绝对值是模型文件相关的**，换量化必须整表重扫。

**库变大的影响**（固定 0.51）：

| 库总条数 | top3 找对 | 真实对话注入率 |
|---|---|---|
| 21 | 11/12 | **36%** |
| 171（≈产品上限 200） | 11/12 | **76%** |
| 521 | 9/12 | 80% |
| 1432 | 6/12 | 87% |

机制（极值效应）：正确答案余弦几乎不动（0.598→0.604），无关消息最高余弦被抬高（0.491→0.582），
**区分度从 0.107 塌到 0.022**。试过均值距与 z 分两种相对判据，都救不回来。

### 3.3 实验三：权重淘汰 vs 时间淘汰

真实库字段形状 + 40 条合成，cap=30，其中三条被 bump 15 次（权重到 1.0）：

| 判据 | 那三条的存活 |
|---|---|
| 按有效权重（新） | **3/3** |
| 若纯按时间 | **0/3**（它们时间上最旧） |

其余：淘汰 31 条、active 剩 30、**不物理删除**（库仍 84 条，只改 `status='evicted'`）、
台账 31 行且 id 与库内一致、身份条目全存活、落盘重读一致。

设计要点：base 权重用 `importance/5` 兜底（facts 无 weight 字段，否则所有人同分 ⇒ 退化成按时间）；
身份条目与 pinned 永不淘汰；衰减公式复用 `memory_events.decayed_weight`（不重写第二套）。

### 3.4 实验四：向量聚类做多维节点（负结果）

`batch` 即「一段对话的一件事」，239 组：

| 指标 | 结果 |
|---|---|
| 同 batch 中位余弦 / 跨 batch | 0.6845 / 0.5025（差 0.182，但分布重叠） |
| **最近邻同实体（top-1）** | **54.4%** |
| top-3 / top-5 含同实体 | 73.6% / 78.7% |
| 层次聚类（0.300 距离阈） | 576 簇，purity 0.758，实体召回 0.502 |
| 压缩比 | **2.4 : 1**（不是 268:1） |
| 聚合的 2-gram 留存 | 中位 **1.00**（簇小+预算够 ⇒ 拼接，不是压缩） |

**决定性证据**：相似度 ≥0.85 的 71 对里，**58%（41 对）是不同具体对象**：

| 余弦 | 一对 | 原文 |
|---|---|---|
| 0.866 | ArcGIS Pro vs MATLAB | 「长期使用 ArcGIS Pro…习惯已保持好几年」/「从本科开始用 MATLAB…好多年」 |
| 0.873 | ArcGIS Pro vs VS Code | 「…写代码到现在基本一直用 VS Code…好几年」 |
| 0.867 | ArcGIS Pro vs WPS | 「用 WPS 已经好多年…」 |
| 0.850 | QGIS vs Blender | 「喜欢 QGIS，开源免费、插件多」/「更偏爱 Blender…插件也多」 |

句式都是「长期使用 X，习惯保持好几年」。⇒ 高相似来自**模板**，不是对象相同。

### 3.5 实验五：抽取侧实体标注（正结果）

两套提示词，各 3 遍（108 批 × 12 条 = 120 次调用）：

| 指标 | A 单 `entity` | B `topic` + `object` |
|---|---|---|
| 覆盖率 | 100% | 100% |
| aspect 合法率 | 100% | 100% |
| 自一致性 | 91.1% | **96.6%**（`object` 单独 96.7%、`topic` 88.1%） |
| 打乱顺序+temp0.3 后一致 | **34.5%** | **74.5%** |
| **判别冲突**（同句式不同对象被归成一个） | **6 组** | **0 组** |
| 归并纯度 | 0.983 | 0.991 |
| 归并召回 | **0.147** | **0.868** |
| key 数（235 条） | 210（过碎） | 111 |
| 同 batch 落同一 key 的比例 | 0.33 | **1.00** |

**方案 A 的 6 组冲突与余弦同病**：`entity='编辑器偏好'` 同时装了 VS Code 与 PyCharm 的条目。
**方案 B 把对象拆出去后冲突归零**：`object` 分别写 VS Code / PyCharm，`topic` 才承担归并。

**增量标注（模拟库增长）**：前半 117 条产出 topic 78 个、object 73 个；
后半 118 条**带上这两份候选表**再标：

| 指标 | 结果 |
|---|---|
| topic 复用率 | **100%**（新建 0 个） |
| object 复用率 | **100%** |
| 跨半 batch 对齐（50 个横跨两半） | **92%**（46/50） |
| 判别冲突 | 5 组（需人工判读，见 §4.3） |

对照：不给候选表时（实验五主表）235 条生成 210 个 key —— 标签会越拆越碎。
⇒ **候选表是必需的**，它把「自由命名」变成「在既有体系里归类」。

**成本**：235 条 × 6 遍 = 120 次调用；输入 63.6k tok / 输出 34.9k tok；约 1.5~1.8 s/批。
推算 1411 条全量标注约 **118 次调用、3~4 分钟、约 ¥0.3**（按本项目历史单价 ¥0.0021/次估算）。

## 4 讨论

### 4.1 词面与向量失败在同一个地方

这是本文最值得记的一条：

| | 词面（2-gram Jaccard） | 向量（bge-small-zh） |
|---|---|---|
| 误连成因 | 共享「慢慢调整」「每周都」等模板片段 | ArcGIS Pro / MATLAB / VS Code 余弦 0.85~0.87（同为「长期使用 X…好几年」） |
| 漏连成因 | 换说法后 2-gram 不重叠（B 档仅认 18%） | 部分改善（12%→95%） |

⇒ 换表示只解决了「换说法」（漏连），没解决「同句式」（误连）。
**误连的本质是「句式相同 ≠ 事情相同」，这是表示层解决不了的，必须引入显式的实体判定。**

这直接推导出实验五的设计：把实体作为一个**字段**显式标注，而不是从文本相似度里推。

### 4.2 为什么 object 比 topic 可靠

`topic`（这类事）天然有歧义：编辑器偏好 / 编辑器使用习惯 / 编辑器配置调整 都可以算同一件事，
也都可算不同。模型在边界上摇摆，自一致 88.1%。
`object`（这个对象）歧义小得多：VS Code 就是 VS Code，自一致 96.7%。

⇒ 设计上应当 **object 当主键、topic 当兜底**：有具体对象就按对象聚合，
泛指偏好（如「爱吃桃片」无更细对象）才落到 topic。

### 4.3 候选表的两面性

给候选表后复用率 100%、跨半对齐 92%，但判别冲突从 0 升到 5。逐条看（已核对的 4 组）：

| key | 两条 | 判断 |
|---|---|---|
| `遥感` | 喜欢遥感原理课程 / 期末遥感考试内容 | **合理合并**（同一门课：偏好 vs 具体事件），机械判据误报 |
| `gis空间分析` | 喜欢这门课 / 用 DEM 做坡度分析作业 | 合理合并 |
| `gis空间分析` | 对课程看法变化 / 用 DEM 做作业 | 合理合并 |
| `gis空间分析` | 用 DEM 做作业 / 在弄 GIS 二次开发卡在图层加载 | **可能过度合并**（课程 vs 开发项目） |

⇒ 机械判据（拉丁专名互斥 ⇒ 不同对象）在「同一主题下的不同技术名词」上会**误报**
（遥感课程里的 GIS 与 NDVI 都是技术词）。5 组里已核对 4 组，3 组是误报、1 组可疑，第 5 组未打印。

**这正是候选表的代价**：它让模型倾向复用，也就更倾向把「差不多」的并进来。
需要一个防过度合并的机制 —— 候选表只给 `object`（歧义小的那个），`topic` 允许自由新建。

### 4.4 容量上限应该长什么样

数据给出的定义：**上限 = 让真实对话注入率仍低于目标值的最大条数**。

这比固定 200/400 更对，而且天然「会成长」：库压得好（同主题归并、细节下沉）区分度高就能装更多；
压得差（同质碎句多）区分度低就自动收紧。

但它要求两件东西：① 能持续测注入率（观测，已落地台账字段）② 一个目标值（建议先设 50%，需 Owner 定）。

## 8 结论

1. **可以给语义检索开绿灯**，但必须带三条：定义式守卫、阈值校准自检、模型缺失时降级回词面。
2. **facts 的容量治理已经落地**（权重 + 台账 + 只标记不删除），并在真实库上验证不误触发。
3. **多维节点不要走「事后聚类」**。要走「抽取侧显式产出 `object`（主键）+ `topic`（兜底）+ `aspect`」，
   并给候选表防漂移；同时要防候选表带来的过度合并。
4. **容量上限的长期形态是「注入率约束」**，需要持续观测 + 一个 Owner 定的目标值。
5. **下一步的最小可验证动作**：在小规模真实对话上验证 `object + topic + aspect` 三字段
   对注入质量的影响（目前只验了标注质量，没验注入效果）。
