## 二、① 统计：92% 这个数的精度

| 口径 | 命中 | 95% Wilson 区间 |
|---|---|---|
| BM25 留出集 | 3/12 = 25% | [9%, 53%] |
| 向量 0.51 留出集 | **11/12 = 92%** | **[65%, 99%]** |
| BM25 开发集 | 2/6 = 33% | [10%, 70%] |
| 向量 0.51 开发集 | 5/6 = 83% | [44%, 97%] |

**两区间不重叠**（向量下界 65% > BM25 上界 53%）⇒ 差异显著，不是采样噪声。

但 92% 这个点数不能当精确值用 —— 真话是「**大概率在 65%~99% 之间**」。
以后引用请写 11/12，别写 92%。

## 三、② 稳健带：余量只有 0.005

按真实 R@3 扫描（步长 0.005，脚本 `reverify_band.py`）：

| 阈值 | holdR@3 | 注入率 | 漏了谁 |
|---|---|---|---|
| 0.435 | 12/12 | 76% | — |
| **0.440 ~ 0.515** | **11/12** | 73% → **36%** | h04 |
| **0.510（当前）** | **11/12** | **36%** | h04 |
| 0.520 | 10/12 | 31% | h04, h06 |
| 0.525 | 9/12 | 29% | h02, h04, h06 |
| 0.545 | 8/12 | 24% | +h05 |
| 0.580 | 6/12 | 20% | +h07, h12 |
| 0.600 | 5/12 | 18% | +h08 |

**当前 0.51 的余量：向下 0.070，向上只有 0.005。**

⚠ 我上轮写「0.51 是最优点」时，只看到了「召回封顶 + 注入率最低」，没算余量。
一句话纠正：**0.51 是「召回不掉的最低注入点」，不是「稳健点」**。

### 3.1 但越界后果是温和的（这点要说清，别把人吓住）

| 越界 | 后果 |
|---|---|
| 向上飘到 0.52 | 召回 11/12 → **10/12（83%）**，注入率 36% → 31%（更省） |
| 向上飘到 0.545 | 8/12（67%），仍远高于 BM25 的 25% |
| 向下飘到 0.44 | 召回不变，注入率 36% → **73%**（记忆过拟合变严重） |

⇒ 危险方向是**向下**（注入率翻倍），向上只是温和降召回。所以 0.51 靠上沿这件事，
风险是「可能少召回一条」，不是「功能崩掉」。据此我不建议为了余量把阈值下移到
0.44~0.47 —— 那会换来 60%~73% 的注入率，正好违反这批改动要治的病。

## 四、③ 换量化：排序稳，数值不稳

下载 `onnx/model.onnx`（fp32，90.5MB）与 int8（22.9MB）对比同一批文本：

| 项 | 结果 |
|---|---|
| top1 命中对象是否相同 | **12/12 完全相同** |
| 逐条余弦差（fp32 − int8） | 中位 **−0.0099**，范围 −0.0277 ~ −0.0029 |
| 方向 | 12 条**全部为负**（fp32 一致更低） |
| 幅度 | 跨度 0.0248，不齐 |

**含义**：
- 语义理解没问题（排序完全一致），但**余弦的绝对值是模型文件相关的**
- 0.51 换了量化就必须重扫，不能平移一个固定量（幅度从 0.003 到 0.028 不等）
- 保守估计：fp32 上应把阈值下移约 0.03

⇒ 我把这条写成了**运行期自检**（见第六节）。

## 五、④ 库规模：这条推翻了我上轮的乐观说法

固定阈值 0.51，真库 21 条 + N 条无关记忆，正确答案始终在库里：

| 库总条数 | top1 找对 | top3 找对 | 真实对话注入率 | 单次延迟 |
|---|---|---|---|---|
| 21 | 10/12 | **11/12** | **36%** | 15.5 ms |
| 71 | 10/12 | 11/12 | 62% | 15.8 ms |
| 121 | 10/12 | 11/12 | 67% | 17.5 ms |
| 171（≈产品上限 200） | 9/12 | 11/12 | **76%** | 16.3 ms |
| 221 | 9/12 | 10/12 | 76% | 18.2 ms |
| 521 | 4/12 | 9/12 | 80% | 21.8 ms |
| 1432 | 4/12 | 6/12 | **87%** | 23.5 ms |

（top1 这一列含「必须过阈值才算」的口径，所以 21 条时是 10/12；
上轮那张表的 11/12 是「top1 正确即算」，两者定义不同，不是数据冲突。）

### 5.1 机制：极值效应

| 库条数 | 留出集 max 余弦中位 | 真实消息 max 余弦中位 | 两者差 |
|---|---|---|---|
| 21 | 0.5975 | 0.4909 | **0.107** |
| 171 | 0.5985 | 0.5681 | 0.030 |
| 521 | 0.6040 | 0.5681 | 0.036 |
| 1432 | 0.6044 | 0.5822 | **0.022** |

正确答案的余弦几乎不动（0.598 → 0.604），但**无关消息的最高余弦被抬起来了**
（0.491 → 0.582）—— 因为「N 条里取最大值」随 N 单调上升。

⇒ 固定阈值的等价含义是「库越大越宽松」，正好与「治记忆过拟合」相反。
这是绝对判据的**结构性缺陷**，不是调参能修的。

### 5.2 试过相对判据，救不回来

| 判据 | 库 21 | 库 171 | 库 521 | 库 1432 |
|---|---|---|---|---|
| A 绝对 cos≥0.51 | 11/12 · 36% | 11/12 · 76% | 9/12 · 80% | 6/12 · 87% |
| B 绝对 + 均值距≥0.15 | 10/12 · 27% | 11/12 · **56%** | 9/12 · 62% | 6/12 · 82% |
| B 绝对 + 均值距≥0.20 | 5/12 · 16% | 6/12 · 31% | 6/12 · 31% | 4/12 · 40% |
| C 绝对 + z≥2.0 | 9/12 · 27% | 11/12 · 76% | 9/12 · 80% | 6/12 · 87% |
| C 绝对 + z≥2.5 | 9/12 · 27% | 11/12 · 69% | 9/12 · 80% | 6/12 · 87% |

（单元格＝留出集召回 · 真实对话注入率）

结论：
- **只有 B（均值距≥0.15）在所有规模上都有改善**（171 条：76%→56%），但 21 条时召回 11→10
- z 分基本无效 —— 因为分母（标准差）随库变大而变，分子分母一起动
- **没有一种相对判据能在四种规模上都同时保住召回和注入率**

⚠ 需要说清的局限：干扰项是 1411 条**同风格无关记忆**（全是「用户喜欢/习惯…」句式），
所以这是**最坏情况**。真实增长会带入相关记忆，不会这么糟。但方向性结论成立。

## 六、按复验结论改了什么（代码）

上轮 `DEFAULT_THRESHOLD = 0.51` 只有一句「实测最优点」。现在补成**带条件的常量**：

```python
CALIBRATION = {
    'model_tag': 'bge-small-zh-v1.5-int8-cls',
    'onnx_mb': 22.9,          # int8 量化版
    'library_size': 21,       # 校准时的事实库条数
    'verified_on': '2026-11-04',
    'band': (0.440, 0.515),   # 留出集 11/12 的阈值区间
}
```

新增 `calibration_warning(onnx_mb)`：模型文件大小与校准时差 >25% 就告警。
加载时自动检查，`status()` 会带出来：

```
向量检索可用（⚠ 模型文件 90.5 MB 与校准时的 int8 版（22.9 MB）差 4.0 倍
                ⇒ 阈值 0.51 可能不适用，请重跑 reverify_models.py 重校准）
```

**为什么按文件大小判**：量化精度没法从权重内容直接看出来，但 int8(22.9MB) 与
fp32(90.5MB) 差 4 倍，足以区分；误差带 ±25% 容得下同量化的不同导出。

新增 4 项测试（`test_calibration_quiet_on_int8_size` /
`warns_on_fp32_size` / `tolerates_bad_input` / `band_is_documented`），
其中最后一项断言「当前阈值必须落在记录的稳健带内」—— 防止以后有人改阈值不同步改文档。

## 七、复验后我的结论

### 7.1 0.51 留不留：留

理由：
1. 召回 11/12 在 0.440~0.515 全区间稳定，0.51 只是其中注入率最低的一档
2. 越界是温和的（向上少召一条、向下注入变多），不是功能崩
3. 往下挪换余量，要用 60%~73% 的注入率买单，与这批改动的目的相反

### 7.2 但使用条件必须写清（已写进代码）

| 条件 | 若违反 |
|---|---|
| 模型必须是这个 int8 文件 | 运行期告警（已实现） |
| 库规模 ~21 条时校准 | 171 条时注入率 76%、1432 条 87% |
| 配定义式提问守卫 | 违反「记忆只作背景不做话题」契约 |

### 7.3 库增长这件事需要一个应对（还没做，也不能在这批做）

固定阈值在库变大时会失效，这是**结构性**的。可行方向（都还没验证）：
- 按库规模动态调阈值（用库自身相似度分布的分位数定标）
- 或者检索时先粗筛 topic（分类字段已有 `cat`），再算余弦
- 或者接受「注入率随库增长」，把它当已知行为而不是缺陷

**这条会直接影响要不要接进产品检索**：现在 21 条库时很好，但库一旦涨到
上百条，「不滥注入」这个目标就会被削弱。接线前必须先定这件事。

### 7.4 复验没能消除的不确定性

| 项 | 状态 |
|---|---|
| 12 条留出集的代表性 | 无法证明。只能靠 95%CI [65%, 99%] 兜着 |
| 真实库涨到 200 条的样子 | 只用合成干扰项估过（最坏情况 9/12 召回 + 76% 注入）|
| fp32 与 int8 谁更准（语义） | 未测。只测了排序一致、数值不同 |
| 多语言 / 英文查询 | 未测（模型是中文专用）|

## 九、本轮我自己犯的三个错（都是「手写结论」）

1. **稳健带算错**：第一版拿「最小正确余弦」当唯一边界，上下界变量写成同一个数，
   还印了「余量够」。真相是**向上只余 0.005**。改成按真实 R@3 扫描。
2. **单条样本外推**：用 1 条样本算出「0.51 在 fp32 上等价于 0.52」，
   而 12 条统计是中位 −0.0099、方向全为负。已撤回并改为逐条分布。
3. **结论与数字相反**：12 条全负差，我印「方向不统一」「有正有负」。
   原因是结论句是**固定文案**，没跟着变量走。

三次都是同一个形状：**先想好要说什么，再把数字填进句子里**。
修法也一样：结论必须由变量插值生成，写完自问「变量反过来这行会变吗」。
