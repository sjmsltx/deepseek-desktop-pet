### 2.2 四条设计决策

**① 上限限制 active 条数，淘汰只改 `status='evicted'`，不物理删除**

理由：「原件保留」是既有纪律；JSON 体积不痛（2 万条约 5MB）。物理删除只省磁盘，丢掉可恢复性。

**② base 权重用 `importance` 兜底**

facts 存量**没有 weight 字段**（只有 importance 1~5）。若直接复用 `effective_weight()`，
所有人 base 都是 `WEIGHT_NEW=0.55` ⇒ 淘汰退化成「换个名字的按时间淘汰」，白做。

**③ 身份条目 / pinned 永不淘汰**

复用 `memory_events.is_identity_entry()`，判据同源。这类条目每轮必在，不能因分数低被挤掉。

**④ 衰减公式复用 `memory_events.decayed_weight`**

不重新实现 —— 两套衰减公式迟早对不上。`test_decay_reuses_events_formula` 钉住这一点。

## 三、你说的「上限可以成长」：数据给出了可测的定义

### 3.1 为什么固定条数上限是错的方向

我原本提「库超 120 条就重新定标」，那是**治标**。真实机制是：

| 库条数 | 真问题 max 余弦 | 闲聊 max 余弦 | 区分度 |
|---|---|---|---|
| 21 | 0.5975 | 0.4909 | **0.107** |
| 171 | 0.5985 | 0.5681 | 0.030 |
| 1432 | 0.6044 | 0.5822 | 0.022 |

**极值效应**：条数越多，闲聊消息的最高余弦被抬得越高（0.491 → 0.582），
而正确答案的余弦几乎不动（0.598 → 0.604）。区分度从 0.107 塌到 0.022。

⇒ 固定阈值的等价含义是「库越大越宽松」，正好与「治记忆过拟合」相反。

### 3.2 所以上限的正确形式是「注入率约束」

```
上限 = 让「真实对话注入率」仍低于目标值的最大条数
```

这个量**可测**（`reverify_scale.py` 能直接跑曲线），而且它自然「会成长」：
- 库压得好（同主题合并、细节下沉）⇒ 区分度高 ⇒ 能装更多条
- 库压得差（同质碎句多）⇒ 区分度低 ⇒ 上限自动收紧

**这比「固定 200」或「固定 400」都更对**，也符合 Owner 说的「成长与遗忘是相对的」。

### 3.3 一个必须先承认的约束

**节点多维化会让条数变多**（一条变多条），而条数变多正是注入率上升的原因。

⇒ 「多维化」和「不滥注入」天然拉扯。所以多维化必须自带**聚合视图**：
- 存的时候是多面向（实体 + 多个 aspect）
- 注入时压成一句（「用户爱吃桃片，偏好甜味、老工艺」＝ 3 个面向压成 1 句）

现在那条桃片记忆就是压过的，但**靠 LLM 抽取时顺手压，不是结构保证**。

## 四、第 2 步建议：容量预算（待批准）

### 4.1 三个候选，我的排序

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 注入率驱动的动态上限** | 定期用真实对话样本测注入率，超目标就降上限 | 直接对齐目标；可测 | 需要真实对话样本；滞后 |
| **B 主题容量预算** | 每 `cat` 类给配额，库满先压缩同类（合并同主题碎句） | 结构上防同质堆积 | 需要合并算法；可能误合 |
| **C 保持固定上限 + 台账观察** | 400 不变，靠台账看实际淘汰曲线再调 | 最简单 | 不解决结构问题 |

**我建议 A + C 组合**：先 C（现在就是），同时按 A 的指标建立观测，
攒够真实数据后再定 B 是否需要。

理由：B 的合并算法风险高（合错了会丢信息，且不可逆），而 A 的指标是**观测**不是**改写**，
零风险。先观测再动结构。

### 4.2 已落地的观测（2026-11-04，Owner 批准「按建议」后完成）

| 改动 | 作用 |
|---|---|
| 台账新增 `active_before` 字段 | 回答「库在多大时开始需要淘汰」—— 只记淘汰后的 `kept` 不行 |
| 新增 `capacity_status(facts, cap)` | 一句话给出 active / cap / free / ratio / need_evict |
| 4 项新测试 | 含「非 active 不占名额」「超容时 need_evict 为真」 |

**只做观测，不改任何行为** —— 上限仍是 400，判据仍是权重。

### 4.3 若将来批准 A，具体做什么

1. 每次淘汰后把「当时库规模 + 注入率估计」记进台账（现在已记 `kept`，加一个 `inj_rate` 字段）
2. 提供 `tools/eval/experiment/scripts/reverify_scale.py` 的定期复跑（人工触发，不自动）
3. 定一个目标注入率（建议先设 **50%**，理由是：真实对话里有一半消息能关联到记忆，
   语义上说得通；超过就该压缩了）

### 4.4 关于 events 的 200 条上限（Owner 说「也按你的建议」）

**这条我要先说清风险，因为改它会动 4 条现有测试的预期。**

现状判据（`memory_events.py` L484）：

```python
kept = others[-keep:]      # 纯按插入顺序，保留最近
```

权重 `effective_weight()` 算了但不参与淘汰。改成权重判据后：

| 现有测试 | 会怎样 | 为什么 |
|---|---|---|
| `test_record_before_delete` | 仍绿 | 只验顺序与条数 |
| `test_pinned_not_in_ledger` | 仍绿 | pinned 豁免不变 |
| `test_ledger_tolerates_missing_fields` | **会红** | 它断言「完整」(10-01, w=0.6) 被淘汰；改判据后它权重 0.286 > 「新的」0.2716，反而留下 |
| `test_evicted_entries_are_recorded` | 可能红 | 依赖具体谁被淘汰 |

**为什么会出现「老的留下、新的被淘汰」**：测试数据的时间是 2026-10-01~04（31~34 天前），
按幂律衰减 34 天后 0.6 只剩 0.286；而「新的」也是 31 天前造的，衰减到 0.2716。
真实运行时「新的」是**现在**写入的（age≈0 ⇒ 0.55），不会被淘汰。所以是测试数据的时间戳造成
的反直觉结果，不是产品缺陷。

⇒ 改 events 判据必须同时改那两条测试的**断言方式**（改成「测意图」而不是「测具体对象」），
并新增一条锁「低权重老条目先走」。这是**改测试**，需要你明确点头。

**我的建议**：events 先别改。理由是 —— events 现在只有 6 条，离 200 还很远；
而 facts 是裸增长（真问题）。先把 facts 跑一段看台账，再决定要不要动 events 的判据。

## 五、第 3 步：节点多维化

> **2026-11-04 二次修正**：初版原型判定「聚类不可行」；后续做了标签修正与密度实测，
> 结论进一步收紧为「**在真实记忆密度下，多维聚合不值得做**」。
> 完整数据见 `实验补完-标签修正与结构化前提-20261104.md`。

### 5.0 价值前提：记忆密度必须够高

多维节点的收益 = 把「同一件事的 N 条记忆」压成 1 条。
所以它成不成立，取决于**平均每件事有几条记忆**（下称「记忆密度」）：

| 数据 | 条数 | 实体数 | 平均每组 | **单体占比** | 聚合后 2-gram 留存 |
|---|---|---|---|---|---|
| 合成库（按对话分组） | 1411 | 239 | **5.9 条** | 0% | 0.17 |
| **真实库（LLM 分组）** | 21 | 18 | **1.2 条** | **83% 组**（71% 条）| **1.00** |


> ⚠ **2026-11-05 勘误**：本行密度/单体数已过时。那 3 个「2 条组」经查是**同 id 两份**（撞号缺陷），
> 不是多面向。真实值是 **18 条唯一记忆 / 18 实体 / 密度 1.00 / 100% 自成一件事**。
> 详见 `勘误-真实库密度-20261105.md`。原数字保留不删，以免丢失历史。

- 合成库 5.9 条/件是**人为造出的高密度**（1411 条按「一段对话 5~9 条同一件事」批量生成）
- 真实库 1.2 条/件，**83% 的组是单体**（15/18；按条数 71%，15/21）
  ⇒ 聚合 = 原样输出（留存 1.00），零收益

⇒ **初版用合成数据量出的「聚合省上下文」在真实场景不成立。**
这一点已落成产品侧的观测指标 `memory_fact_evict.memory_density()` +
`DENSITY_STRUCTURE_MIN = 2.0`，标签覆盖不足 80% 时返回「不可判定」。

**结论：等真实使用的记忆密度观测到 >2.0 再做多维聚合。**

## 五之二、第 3 步原型细节（**聚类路线为负**）

> 完整数据见 `多维节点-原型报告-20261104.md`。这里只放结论。

### 5.1 原型做了什么

用 `memories-1411.json` 的 `batch` 字段（239 段对话，每段 = 一件事的多个面向）当真值，
测「仅用向量能否还原实体结构」。

### 5.2 结果：不能

| 判据 | 数据 | 含义 |
|---|---|---|
| 最近邻同实体率（top-1） | **54.4%** | 近一半的「最近邻」是别的事 |
| 高相似对（≥.85）里不同对象占比 | **58%**（41/71） | 高相似主要来自**句式模板** |
| 聚类 purity / 实体召回 | 0.758 / 0.502 | 两头都不合格 |
| 压缩比 | **2.4 : 1** | 收益很小 |
| 聚合的 2-gram 留存 | 中位 1.00 | 因为簇小，这不是压缩是拼接 |

**最关键的一组样例**（全部是不同工具，余弦却 0.85~0.87）：

```
「长期使用 ArcGIS Pro…习惯已保持好几年」
「从本科开始用 MATLAB…好多年」                    cos 0.866
「写代码到现在基本一直用 VS Code…好几年」          cos 0.873
「用 WPS 已经好多年…」                            cos 0.867
```

⇒ 同源问题：算法抓的是**句式**（「长期使用 X，习惯保持好几年」），不是「说的是哪件事」。
之前 Jaccard 如此，换 embedding 只是换了个抓手。

### 5.3 对设计的影响（这是原型的真正产出）

1. **实体键必须在抽取阶段显式产出**（`entity` 字段），不能事后用余弦聚类
2. **面向（aspect）由抽取侧枚举**，不用无监督发现 —— 类别有限且可枚举
3. **聚合摘要必须 LLM 写，且保留可回溯原句** ⇒ 聚合只是注入视图，原节点必须留着
   （与已落地的「只改 status 不物理删除」一致）
4. 下一步应做**抽取侧可行性验证**（1411 条让 LLM 只标 entity + aspect，测一致性与成本），
   再谈是否动产品数据结构

### 5.4 影响面（未变）

| 层 | 改动 | 影响面 |
|---|---|---|
| 数据结构 | 节点加 `aspects[]`（面向）与 `stages[]`（阶段） | 44 条存量要迁移 |
| 抽取 | LLM 输出从「一句话」改为「实体 + 多面向」 | `EXTRA` prompt + 抽取测试 |
| 检索 | 按面向 / 阶段命中，而非整句匹配 | `memory_engine` + 注入点 |
| 聚合 | 注入时压成一句 | 新增 |
| 星图 | 节点大小/颜色按面向数 | `memory_starmap` |
| 测试 | 大量夹具要改 | 2332 项 |

**这不是「加参数」，是改核心数据结构。** 按项目规矩必须先出详细设计再动手。

### 5.5 原计划的探索路径与实际结果的差别

原计划（写在本节 5.1 之前）是「用实体聚类把 1411 条聚成 ~200 个实体」。
**原型跑完后这条计划被否掉了**：聚类在簇数接近真值时 purity 只有 0.758、实体召回 0.502，
且压缩比仅 2.4:1。原因不是参数没调好，而是余弦抓的是句式模板（§5.2 的 ArcGIS/MATLAB 那组）。

⇒ 修正后的下一步不是「换个聚类参数」，而是**把实体判定挪到抽取侧**：
让 LLM 在抽取时显式输出 `entity` 与 `aspect`，再用离线数据测标注一致性。
这仍然只是实验，不动产品库。
