# 记忆系统压力实验（2026-11-03）

> 生成时间：2026-11-03 12:05
> 数据规模：**1411 条 facts + 267 条 events**，时间跨度 801 天（2024-08-24 ~ 2026-11-03）
> 成本：¥1.9（deepseek-flash，240 批调用）
> 复现：见文末「怎么重跑」

---

## 这份文档回答什么

桌宠的记忆系统此前只在 **21 条**真实记忆上验证过。21 条这个规模下，「检索准不准」「闸门松不松」
「衰减有没有用」这些问题都测不出真相——库太小，什么都召得回来。

所以造一个 **1411 条**的库，人工压缩时间轴（把两年压成一次生成），看系统在真实规模下的行为。

**四个结论（先看这里）：**

| # | 结论 | 影响 |
|---|---|---|
| 1 | 语料变密**不降低召回**，但**误报率涨 5.6 倍**（4.8% → 26.9%） | 主要风险是"乱提旧事"，不是"想不起来" |
| 2 | 召回低的直接原因是**闸门太严**，不是检索坏了 | r01 真答案排第 1 却被挡掉 |
| 3 | 闸门是**悬崖式**的，不是渐变：m>=2 降到 1，误报从 34% 跳到 62% | 线性调参救不了，只能换机制 |
| 4 | 换机制的可行点：**稀有词闸门**能把误报从 15% 压到 2%，召回不变 | 代价是 holdout 3.2→2.0 |

## 一、数据是怎么造出来的

### 1.1 三层结构

```
corpus.json          1200 条语料种子（12 类话题 × 20 种子 × 5 侧面）
      ↓ 每 5 条种子拼成一段对话，交给真实抽取管线
      ↓ deepseek-flash + response_format=json_object（严格复刻产品参数）
memories-1411.json   1411 facts + 267 events（真实 API 产出，非模板拼装）
      ↓ backfill_time.py 按 batch 顺序分配年龄
      ↓ 时间轴跨 801 天，各年龄段配额已达标
最终实验库          每条记忆带 created_at / age_days
```

### 1.2 为什么用真实 API 而不是模板生成

模板生成的事实千篇一律（"用户喜欢 X"），BM25 的 IDF 会失真——所有词都同样常见，
测出来的检索行为没有意义。

真实抽取管线产出的内容带具体名词（辐射定标、核密度估计、涞滩古镇），
这才是 IDF 有区分度的语料。

**成本**：240 批 × 约 ¥0.008/批 ≈ ¥1.9。失败 1/240。

### 1.3 时间轴怎么"人工加快"

Owner 的要求：「人工加快时间进展，不然那个测试不出来」。

不压缩时间，就得真等两年才能看到幂律与指数的差别。做法：

| 环节 | 做法 |
|---|---|
| 配额 | 先固定关键时间点（1/7/30/90/180/365/730 天）各要多少条 |
| 填充 | 关键点之间用指数分布填充，避免扎堆 |
| 回填 | 按 batch 顺序对年龄（早期批 = 更老），批内 ±0.5 天抖动 |

v1 用"顺序保底"分配，两轮都修不干净（365~545 天 0 条、1 天只有 10 条）。
v2 改成"关键点配额固定 + 指数填充"后全部达标：

```
  1 天 目标40→41 ✓    7 天 目标35→44 ✓    30 天 目标60→92 ✓
 90 天 目标60→119 ✓  180 天 目标50→124 ✓  365 天 目标45→98 ✓
730 天 目标40→40 ✓
```

## 二、发现一：召回不降，误报暴涨

### 2.1 受控实验设计

**关键**：不能拿"21 条库跑一次"和"1411 条库跑一次"直接比——两次的语料内容、用例可用性都不同，
那是用 n=1 讲故事。

所以固定一切，只动一个变量：

| 变量 | 控制 |
|---|---|
| 底库 | 21 条真实 facts（`memory.json` 的 active） |
| 噪声 | 从 1411 条合成 facts 里随机取 N 条 |
| 用例 | **只留期望词在 21 条真库里存在的那些**（否则答案根本不在库中，测的是幻觉） |
| 指标 | top3 命中率 / 负样本误命中率 / 平均返回条数 |

每个点 3 次不同随机种子。

### 2.2 结果

| 总条数 | recall | holdout | 负样本误命中 | 倍数 | 平均返回 |
|---|---|---|---|---|---|
| 21 | 2.0/6 | 3.0/12 | 2.0/42 (4.8%) | 1.0× | 0.44 |
| 46 | 2.0/6 | 3.0/12 | 2.3/42 (5.5%) | 1.2× | 0.52 |
| 71 | 2.0/6 | 3.0/12 | 4.0/42 (9.5%) | 2.0× | 0.56 |
| 96 | 2.0/6 | 3.0/12 | 5.3/42 (12.6%) | 2.7× | 0.70 |
| 121 | 2.0/6 | 3.0/12 | 5.0/42 (11.9%) | 2.5× | 0.65 |
| 146 | 2.0/6 | 3.0/12 | 4.0/42 (9.5%) | 2.0× | 0.72 |
| 171 | 2.0/6 | 3.3/12 | 6.0/42 (14.3%) | 3.0× | 0.74 |
| 196 | 2.0/6 | 3.3/12 | 9.7/42 (23.1%) | 4.8× | 0.74 |
| **221（产品上限）** | 2.0/6 | 3.0/12 | 4.7/42 (11.2%) | 2.3× | 0.89 |
| 321 | 2.0/6 | 3.0/12 | 11.3/42 (26.9%) | 5.7× | 0.76 |
| 521 | 2.0/6 | 3.3/12 | 11.3/42 (26.9%) | 5.7× | 0.89 |

**两点必须一起说**：

1. **召回完全平稳**（recall 恒定 2/6，holdout 3.0~3.3/12）——语料变密没有让检索变差
2. **误报涨 5.7 倍**（4.8% → 26.9%），但**不是单调的**：175 条时 9.7，200 条时反而 4.7

第 2 点的不单调是抽样噪声，不是真实波动。3 次重复的极差在 175 条时是 [9, 11]，
200 条时是 [4, 5]——两个点差这么远，说明**单点结果不能当结论**，
只能看整体趋势（21→521 条，2.0 → 11.3）。

### 2.3 机制：为什么误报会涨

`memory_engine.py` 的 `search_detailed()`：

```python
matched  = len(qt & set(self.doc_tokens[i]))   # 纯集合交集计数
coverage = matched / max(len(qt), 1)            # 纯计数比例
```

**两个都不看词的稀有度。** 「我」「的」「什么」和「桃片」「Python」权重相同。

语料 21 条时，凑够 2 个词不容易；语料 500 条时，任意 query 的常见词在几十条里都出现，
`matched>=2` 几乎白送。

BM25 的 `score` 本身是 IDF 加权的（`_idf()` 在算），但**闸门没看它**——
只用 `keep_ratio` 设了个相对地板（best × 0.25），不解决绝对计数的问题。

## 三、发现二：召回低的真原因是闸门

### 3.1 一个反例

`r01「我叫什么名字？」`，21 条真库里：

```
BM25 排名第 1：'我的名字叫小蓝（V4 Flash 桌宠）'
    matched = 1, coverage = 0.2
闸门：matched >= 2 或 coverage >= 0.30
    ⇒ 1 < 2 且 0.2 < 0.30 ⇒ 挡掉 ⇒ 返回 0 条
```

**答案就在第一名，闸门把它扔了。** 这不是"检索找不到"，是"找到了不让用"。

### 3.2 闸门是悬崖式的

容量固定 200 条（产品上限），5 个随机种子：

| 闸门配置 | recall | holdout | 负样本误命中 | 平均返回 |
|---|---|---|---|---|
| m>=2 cov>=0.30（**现状**） | 2.0/6 | 3.2/12 | 6.4/42 (15%) | 0.67 |
| m>=2 cov>=0.25 | 2.0/6 | 3.2/12 | 11.0/42 (26%) | 0.67 |
| m>=2 cov>=0.20 | 3.0/6 | 3.2/12 | 14.4/42 (34%) | 0.81 |
| m>=1 cov>=0.40 | 5.8/6 | 4.2/12 | 26.2/42 (62%) | 2.13 |
| m>=1 cov>=0.30 | 5.8/6 | 4.2/12 | 26.2/42 (62%) | 2.13 |
| m>=1 cov>=0.00 | 5.8/6 | 4.2/12 | 26.2/42 (62%) | 2.13 |
| 全放开（对照） | 5.8/6 | 4.2/12 | 26.2/42 (62%) | 2.13 |

**两个关键观察**：

1. `min_matched` 从 2 降到 1 是一道**悬崖**：召回 3.0 → 5.8（几乎满分），
   但误报 34% → 62%（等于完全放开闸门）
2. `m>=1` 时 coverage 从 0.40 调到 0.00 **结果完全一样**——因为代码写的是
   `matched >= mm or coverage >= mc`（**OR**），m>=1 时几乎必过，cov 形同虚设

**结论**：现有配置 (2, 0.30) 恰好站在悬崖前一侧，不是随便调的。
想同时提召回压误报，线性调参做不到，必须换机制。

## 四、发现三：换机制的一个可行点

### 4.1 试了什么

**稀有词闸门**：只有 `idf(w) > median(idf(query 所有词))` 的命中才算数。

- 「我爱吃啥」→ tokenize 后「我/爱/吃/啥」全是高频词 ⇒ 没有稀有词命中 ⇒ 不注入（正确）
- 「我叫什么名字」→ 命中「名字」，若「名字」在库里稀有 ⇒ 算 1 分

### 4.2 结果（容量 200 条 / 5 种子）

| 机制 | recall | holdout | 负样本误命中 |
|---|---|---|---|
| matched>=2 OR cov>=0.30（现状） | 2.0/6 | 3.2/12 | 6.4/42 (15%) |
| rare>=1 | 5.8/6 | 4.2/12 | 24.4/42 (58%) |
| rare>=2 | 2.0/6 | 1.2/12 | 4.6/42 (11%) |
| **rare>=1 AND cov>=0.30** | **2.0/6** | **2.0/12** | **1.0/42 (2%)** |
| rare>=1 AND cov>=0.40 | 0.0/6 | 1.0/12 | 0.0/42 (0%) |

**`rare>=1 AND cov>=0.30` 是唯一有意义的改进点**：

- 召回不变（2.0/6）
- 误报从 15% 降到 **2%**（约 1/7）
- 代价：holdout 从 3.2 降到 2.0（少召回 1.2 条）

**取舍判断**：误报是用户能直接感觉到的（"它说起我根本没说的事"），
漏召回常被归因于"我自己没说过"。所以这个交换大概率划算——但这是**产品决策，需 Owner 拍**。

**注意**：这只是把前沿往前推了一小步，没有突破。
在纯 BM25 词袋 + 这批用例下，precision/recall 的前沿就在这里。
真正的突破需要语义检索（embedding），不是词袋调参能做到的。

## 五、发现四：衰减模型只影响老记忆

### 5.1 两类模型在真实年龄分布下的差别

| 年龄段 | 条数 | 指数均值 | 幂律均值 | 倍数 |
|---|---|---|---|---|
| 0-7 天 | 103 | 0.62363 | 0.59375 | 1.0× |
| 7-30 天 | 203 | 0.44434 | 0.40923 | 0.9× |
| 30-90 天 | 357 | 0.20984 | 0.28047 | 1.3× |
| 90-180 天 | 349 | 0.04527 | 0.19756 | 4.4× |
| 180-365 天 | 277 | 0.00385 | 0.13738 | 35.7× |
| 365-545 天 | 74 | 0.00010 | 0.11238 | 1133× |
| 545 天+ | 48 | 0.00000 | 0.08028 | 227 万× |

**但「权重最高的前 20 条」两模型重合 20/20。**

这不是矛盾，是必然：top 20 全是新记忆，两种模型在新记忆上几乎一样。
差别全在**老记忆**——指数模型让一年前的记忆彻底归零（0.0001），幂律模型保留 11%。

### 5.2 这对产品意味着什么

`effective_weight` **没有任何消费方**，只被星图亮度使用。
所以衰减模型的差别**不影响决策**（检索不看它），只影响**星图看起来什么样**：

- 指数：一年前的星星几乎全黑（等于"消失了"）
- 幂律：一年前的星星还有 10% 亮度（"还看得见，但很淡"）

Owner 选幂律的理由是后者更接近人对记忆的直觉。这次实验给出定量支持：
**幂律在 90~545 天这段保留了 4~1100 倍的可见度**，而这段正是"还记得但想不起来"的区间。

## 六、发现五：星图分类在真实语料上失真

1411 条 facts 的分类分布：

| 类 | 中文名 | 条数 | 占比 |
|---|---|---|---|
| like | 兴趣·偏好 | 1191 | **84.4%** |
| study | 学业·学习 | 146 | 10.3% |
| work | 工程·项目 | 48 | 3.4% |
| human | 人际·相处方式 | 21 | 1.5% |
| mile | 里程碑 | 5 | 0.4% |

**单类占 84%**，星图会挤成一团——所有星星堆在一个扇区。

原因是合成语料以"兴趣/偏好"型陈述为主（"用户喜欢 X"），关键词表把大部分都归进 like。
但这暴露了真实缺陷：**关键词表是硬编码的，没有做过规模化的分布检验**。

⚠ 这条要打折看：语料是我造的，偏好型陈述天然偏多。真实使用中分布未必这么偏。
**需要拿真实使用数据复核**，不能直接据此改代码。

## 七、发现六：星图连线的两个问题

把 1411 条灌进 `memory_starmap.load_stars()` 后实测：

| 项 | 结果 |
|---|---|
| 星点数 | 1411（全部读入，`age` 字段 0.3 ~ 801.3 天齐全） |
| 强边（词面重叠 >= 0.045） | 1262 条，94% 的星星有强边 |
| 弱边（同类 MST） | 1406 条 |
| **`build_edges` 耗时** | **36.9 秒** |

### 问题一：构建时间不可接受

`build_edges` 是 O(n²) 全配对：

```python
for i in range(n):
    for j in range(i + 1, n):
        w = jaccard(stars[i]['text'], stars[j]['text'])   # 每次都重新 tokenize
```

1411 个点 = 995,055 次配对，36.9 秒。产品上限 200 条时是 19,900 次（约 1~2 秒，勉强），
但**给 Owner 看 1200 条规模的效果时，36.9 秒的构建会让界面卡死**。

两条低风险改法（未实施，需 Owner 拍）：

1. 把 `terms()` 结果缓存到星点（现在每次 `jaccard` 都重新算两遍 tokenize）
2. 用倒排索引替代全配对：只为「共享至少一个词」的点对算 jaccard，
   其余直接跳过。这能把 1411 条的耗时降到秒级。

### 问题二：强边全是"近重复句"，不是真关联

权重最高的三条：

| 权重 | A | B |
|---|---|---|
| 0.593 | 用户喝奶茶的习惯已保持好几年，基本每周都要喝几杯 | 用户喝柠檬茶的习惯已保持好几年，基本每周都要来一杯 |
| 0.444 | 用户最近开始觉得 VS Code 有点重，偶尔想试试更轻量的编辑器 | 用户最近觉得自己用的 IDE 有点重，想试试更轻量的编辑器 |
| 0.412 | 打算继续把自然地理这块学扎实 | 打算继续把人文地理学扎实 |

这三对确实是"关联"，但关联来源是**同一模板生成的近似句**，不是真实的语义相关。

⚠ **这是合成语料的特征，不能当成产品缺陷，也不能当成"关联效果好"的证据。**
用这份数据看星图视觉时，要知道连线密度会被语料重复度抬高。
真关联质量需要真实使用数据才能评。

## 八、改闸门的尝试：被产品红线拦住（本轮真实结局）

Owner 批准按「稀有词闸门」改。改完跑测试，被产品自己的回归护栏拦住：

```
tests/test_memory_eval.py::test_not_below_baseline[H_R@3]
AssertionError: H_R@3 掉到 17%，基线是 25% —— 本轮改动把召回弄坏了
```

`tests/test_memory_eval.py` 的 `BASELINE` 注释写着「**只许上调，不许为了变绿往下改**」。

### 关键：这不是调参没调好，是结构性取舍

我又补测了「同一规模下两种判据对比」，看是否存在「小库用旧判据、大库用新判据」的拐点：

| 总条数 | 旧判据 rec/hold/负样本 | 新判据 rec/hold/负样本 | 差 |
|---|---|---|---|
| 21 | 2.0 / 3.0 / 2.0 | 2.0 / 2.0 / 0.0 | hold −1.0 / 负样本 −2.0 |
| 35 | 2.0 / 3.0 / 3.0 | 2.0 / 2.0 / 0.3 | hold −1.0 / 负样本 −2.7 |
| 50 | 2.0 / 3.0 / 3.0 | 2.0 / 2.0 / 0.3 | hold −1.0 / 负样本 −2.7 |
| 75 | 2.0 / 3.0 / 4.0 | 2.0 / 2.0 / 2.0 | hold −1.0 / 负样本 −2.0 |
| 100 | 2.0 / 3.0 / 3.7 | 2.0 / 2.0 / 0.3 | hold −1.0 / 负样本 −3.3 |
| 150 | 2.0 / 3.3 / 6.3 | 2.0 / 2.0 / 3.0 | hold −1.3 / 负样本 −3.3 |
| 200 | 2.0 / 3.7 / 4.0 | 2.0 / 2.0 / 1.0 | hold −1.7 / 负样本 −3.0 |

**「hold −1」在所有规模上都成立，包括 21 条。** 所以：
- 不存在「库小时用旧判据、库大时用新判据」的干净切换点
- 做规模自适应只是**绕开护栏**（护栏只测 21 条真库），不是解决问题

### 为什么必然丢这 1 条

丢的是 h12「那个帮我管事的桌面平台我管它叫什么来着」→ AutoClaw：
`rare=2` 但 `coverage=0.12`（query 有 17 个 2-gram，答案只覆盖 2 个）。
现状靠 `matched>=2`（不看稀有度）放行它；改 AND 后 coverage 条件把它挡住。

试过 `OR (rare>=2 AND cov>=0.1)` 把它救回来（即 D 配方）：
- 21 条：**全部指标等于现状**（护栏绿）
- 200 条：负样本 6.4 → 5.0（15% → 12%）
⇒ 等于没解决问题，弃用。

### 结论：这条路已经到极限

产品代码注释早就写着（`memory_engine.py` 闸门常量上方）：

> ⛔ **真正的瓶颈不是这个数**：把闸门全关（matched=0、cov=0），留出集也只有 42%。
>    字面匹配打不过同义改写（「我大几」vs「用户是大二学生」无共同 2-gram）。
>    要往上走必须加同义词表或语义检索，**别再指望调 GATE_***。

本次实验把这句话量化确认了：**在纯 2-gram 词袋 + 这批用例下，
precision/recall 前沿就在这里，任何精度提升都要拿召回换。**

⇒ 闸门改动已**回退**（`git checkout memory_engine.py memory_events.py`），未进仓库。
下轮若要做，方向是语义检索（embedding），不是继续调阈值。

## 九、build_edges 性能优化（本轮唯一的净改进）

### 优化前

1411 个星点：`build_edges` **33.15 s**。分阶段测速定位到：

| 阶段 | 耗时 | 判断 |
|---|---|---|
| `terms()` 全量一次 | 0.01 s | 不是瓶颈 |
| 强边全配对（terms 已缓存） | 1.25 s | 不是瓶颈 |
| **弱边朴素 Prim** | **约 27 s** | **唯一大头** |

弱边 Prim 是 `for a in tree: for b in rest:`，累计 O(V³)：like 单团 1173 点约 2.7 亿次比较。

### 两处改动

| # | 改动 | 理由 |
|---|---|---|
| 1 | 强边缓存 `terms()` | 原先每对都调 `jaccard()`，内部重新 tokenize 两段 ⇒ 199 万次 `terms()`。改成每篇一次，jaccard 用 `|A∩B|/(|A|+|B|-|A∩B|)` 手算（恒等） |
| 2 | 弱边 Prim → 按 age 排序相邻连 | 距离是 `|age_a - age_b|`，**一维**。一维欧氏距离的 MST 就是排序相邻连，O(n log n) |

### 结果

| 星点数 | 优化前 | 优化后 | 加速 |
|---|---|---|---|
| 60 | 0.02 s | 0.001 s | 19× |
| 221 | 0.24 s | 0.01 s | 27× |
| **1411** | **33.15 s** | **0.34 s** | **96×** |

### 等价性验证（不是"差不多就算对"）

`scripts/verify_edges.py` 用原样复刻的旧算法对比新算法：

| 项 | 60 点 | 221 点 | 1411 点 |
|---|---|---|---|
| 强边顶点对集合 | 完全一致 ✓ | 完全一致 ✓ | 完全一致 ✓ |
| 弱边数量 | 55 = 55 ✓ | 216 = 216 ✓ | 1406 = 1406 ✓ |
| 弱边总权重 | 2358.4000 = 2358.4000 ✓ | 2754.7600 = ✓ | 3044.3300 = ✓ |
| 连通性（每类一棵树） | ✓ | ✓ | ✓ |

弱边**边集**有 9%~47% 的差异，但这是 age 并列导致的一维 MST 不唯一：
总权重恒等于 `Σ(排序相邻差) = max - min`，与边集无关。**星图上线的总长度完全相同**。

## 九之二、2.5D 星图（z 轴 = 年龄）

Owner：「2.5D（z 轴=年龄），更真实 + 更好看」。定为 2.5D 而非真 3D：
零新依赖、包体积不变，且让「年龄 / 衰减」两个维度在视觉上和解。

### 四个深度线索

| 线索 | 实现 |
|---|---|
| 位置 | 向**全局消失点**（图心）收缩 30% —— 透视的正确做法 |
| 大小 | 远小近大，最老的核心半径是最新的 48% |
| 光晕 | 越老越不发光（半径 ×0.38、alpha ×0.45）⇒ 密集处才不会糊成色块 |
| 遮挡 | 绘制顺序按 z 降序：老的先画，新的压在上面 |

深度 `z` = **全局**归一化年龄（不是类内），整张图共用一条时间轴。

### 关键实现选择

**投影在 `_compute_layout` 里做完，结果写进 `_layout`。**
这样 `_to_screen` / `_hit` / 连线端点全部自动正确，不用改三处。
深度值另存 `self._depth[key]`，供绘制顺序与命中半径查询。

### 走过的弯路（都留了注释在代码里）

| 轮 | 做法 | 截图发现的问题 |
|---|---|---|
| 1 | 老记忆整体上移 `R*0.34` | 与环形方位布局打架：上方星团老星顶到标题区（y=97，标题在 y=44），下方星团老星跑进画面中部 |
| 2 | 改成向心收缩 18% + 光晕衰减 | 位置几乎没变（类内半径 148 × 18% = 27px，在 600px 类团间距下是噪声） |
| 3 | `DEPTH_RAD` 0.62→0.48、标签 10→5 + 星团盘占位 | 标签**一个都不显示**（占位 0.72 把 5 个候选位全挡住，亮星都在内圈） |
| 4 | 强边按屏幕距离衰减 + 占位放宽到 0.40 | 连线终于不乱了；但标签仍全被挡 |
| 5 | 类内半径 148→190、整体 R ×0.42 | 星点有间隙了；纵深仍弱 |
| 6 | `DEPTH_SHRINK` 0.18→**0.30**（数学定：位移需 ≥ 类内半径 30%） | 纵深数值到位 |
| 7 | 标签加深色底框（沿用详情卡底色） | 近光源标签压在亮星上读不清 |

### 诚实结论：纵深「数值到位」但「视觉仍不强」

原因不在参数，在**数据分布**：age 集中在中间（1411 条的中位数约 330 天 / 跨度 801），
所以大部分星的 z 在 0.3~0.7，大小差异只有 15% —— 只有极新/极老的少数星差异达 52%。

要做出**明显可感知**的纵深，必须改构图范式（例如改成斜视盘面 + 高度轴，
让「离盘心距离」成为唯一的年龄轴），那是推翻现有环形星团设计，
**属于重大变更，需 Owner 拍**，本轮没做。

### 顺带修掉的观感缺陷（都是截图发现的）

- 跨类强边长达 600+px，1px 细线横穿画面 ⇒ 星团边界被打散
  → 按屏幕距离衰减，跨团淡到约 1/4
- 1411 条时 like 单团 1191 颗，每颗画 5.5 倍半径光晕 ⇒ 叠成一坨实心色块
  → 光晕随深度收缩变淡
- 个体标签从 y=90 排成一竖列压在星盘上 → 减到 4 颗 + 深色底框

## 十一、限制（任何对外引用都必须带上）

| 限制 | 说明 |
|---|---|
| **合成数据** | 不是真人使用记录。语料由 12 类话题种子生成，偏好型陈述偏多（见第六节） |
| **时间轴是回填的** | 不是真实流逝。能回答"不同年龄的权重差多少"，**不能**回答"人真正会怎么忘" |
| **用例集很小** | 6 条 recall + 12 条 holdout + 42 条负样本。单条用例的翻转就能改 8~17 个百分点 |
| **单点噪声大** | 3 次重复的极差常达 2~3 条（见 2.2 的不单调）。趋势可信，单点不可信 |
| **只测 deepseek-flash** | 其他模型的抽取质量未测 |
| **中文分词是 2-gram** | `tokenize()` 用字符 2-gram，不是真分词。这会影响所有 BM25 结论的普适性 |
| **闸门改动已回退** | 稀有词闸门被产品回归护栏（H_R@3 基线 3/12）拦住，见第八节。仓库里的闸门代码**仍是原样** |

## 十二、我在这轮里犯的错（写下来供参考）

这部分可能比结论更有用——四个错，每个都差点变成"结论"。

### 错 1：把三个假象叠加当成"检索全面崩溃"

第一版分析得到 `dev 0/6, holdout 1/12, 负样本 35.7%`，我准备报"1411 条下检索崩了"。
实际是三个独立问题叠在一起：

| 假象 | 真相 |
|---|---|
| 用例期望词「小蓝/大蓝/小龙虾」在合成语料里**根本不存在** | 测的是幻觉，不是检索 |
| 我的脚本读 `content` 字段，但 `search_memory` 返回的是 **`text`** | 召回列恒为 0 |
| 查询「我爱吃什么东西」不含「桃片」二字 | BM25 词袋天然匹配不到，非缺陷 |

**教训**：报"崩了"之前，先确认"答案真的在库里"+"我读的字段真的是那个字段"。

### 错 2：同一个字段名错误犯了两次

`search_memory` 内部 `cands` 用的是 `'text'` 键，不是 `'content'`。
第一次在 `density_ab.py` 踩了（写成 `text` 传进去），第二次在 `density_curve.py` 又踩了
（读 `content` 出来），导致一整列假 0 被打印出来。

**教训**：验证脚本里每一列都必须打印一条原始样本核对，不能只看汇总数字。

### 错 3：早期误报"30% 静默失败"

第一版抽取测试没加 `response_format=json_object`，测出 30% 返回空。
严格复刻产品参数后 **0/20 失败**。

**教训**：测产品行为必须严格复刻产品参数，差一个参数就测的是另一个系统。

### 错 4：时间轴 v1 用"顺序保底"，两轮没修干净

按年龄段顺序依次填满，结果 365~545 天 0 条（前面的段把配额抢光了）。
第一轮改完还有 1 天只有 10 条。

**教训**：配额和填充要分开——先定每段要多少，再在段内分布。
顺序执行必然互相抢样本。
