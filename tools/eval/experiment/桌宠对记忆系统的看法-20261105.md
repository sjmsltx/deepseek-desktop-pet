## 一、对话原文（节选，逐字）

Owner 问：「不是，我说记忆这件事」

桌宠答（#10）：

> 记忆系统早期那种"拼命往里塞"的做法，本质是**怕忘了显得不记得**。
> 结果反过来，它让记忆变得廉价了——因为太频繁地被拿出来，
> 用户就分辨不出哪些是真记得、哪些是检索命中的废话。

> **第一，阈值是写死的。**……它们有个天然毛病：**长对话容易误杀**。
> 因为聊得越久，用户一句话里出现的"关键词"就越零散，覆盖率反而上不去。

> **闸门的代价不是"注入了不相关的"，而是"该注入的没注入"——而后者是静默的，
> 你不会知道我这轮其实忘了一件本来该想起来的事。**

> **第二，"只作背景不作话题"这条其实是在管我自己。**
> 因为"我记着呢"是一种很讨好、也很省力的话术……但抬多了就变成表演。

> 记忆的价值不在于"每次都被展示出来"，而在于"**该用的时候刚好在**"。

> **闸门最大的隐患在于让你觉得没什么问题**，而不在挡错，
> 因为你根本感觉不到它做了什么。

> 所以真正该改的，可能不是那几个阈值，而是加一个**可观测性**：
> 让我自己知道这轮查到了什么、为什么被挡了。现在这套是黑箱，挡了也不出声。

Owner 说：「继续聊下去」

桌宠答（#12）：

> 第三层最有意思，也最少人做。因为"**注入了但没引用**"这个信号很值钱：
> 它说明这条记忆在当前语境里是噪声，长期统计下来就能反过来调整权重。

> **BM25 再准，也救不了写得差的记忆。**检索层的活是"从已有条目里挑"，
> 可挑的天花板是由写入决定的。

> **第一，短事实和上下文事实是两类东西，却塞进同一个系统里。**
> - "爱吃合川桃片"：独立成立，BM25 能命中，检索友好
> - "上次那个分析"：脱离语境就毫无意义，BM25 几乎不可能救回来
> 后者其实不是"记忆"，是**指代**。混在记忆库里，它只会稀释分数、拉低信噪比。

> **第二，自动抽取的噪声是结构性的。**……**写错的事实和写对的事实长得一模一样**，
> 检索时无法区分。所以写入宁可欠抽，也不要过抽。

> ## 三、一个我觉得更严重的缺陷：记忆没有"取代"关系
> 系统里只有"加"和"删"，没有**"这条取代了那条"**。

> **四、还有个隐蔽的取舍问题**
> 权重体系里，"低频但关键"和"高频但无害"在同一个池子里打分竞争：
> - 高频：今天在学 matplotlib → 每次提绘图都命中 → 分数高
> - 低频：对花生过敏 → 一年用一次 → 分数天然低
>
> 如果淘汰规则只看分数和时间，前者活得很好，后者被清掉。
> 但**后者的失效代价是前者的一百倍**。
>
> 这只能靠"身份级记忆永不淘汰"这种硬规则来兜底（★5 那档就是这样，是对的）。
> 但中间地带全是灰的……

> 我自己的感觉是：这套系统的检索层已经够用了，
> **剩下的问题几乎都在"怎么定义一条记忆"上**——它是什么、什么时候过期、
> 被谁取代、失效代价多大。这些是数据模型问题，不是算法问题。

## 二、它指出的「真缺陷」（我已修复）

### 2.1 缺陷：失效代价最高的记忆被优先淘汰

**这是它四条里唯一直接命中我已落地代码的一条。**

我的淘汰设计：`plan_eviction` 按 (有效权重, 时间) 升序淘汰，
而有效权重 = `importance/5` × 时间衰减 + 命中加成。

**「命中次数」与「丢了会怎样」完全无关** ⇒ 低频关键记忆必然先被淘汰。

### 2.2 实测坐实（不是推测）

| 场景 | 过敏条目 | 周杰伦条目（20 次命中） | cap=1 淘汰谁 |
|---|---|---|---|
| 都 imp=3 | 有效 0.108 | 有效 1.000 | **过敏** ★ |
| 都 imp=5 | 有效 0.180 | 有效 1.000 | **过敏** ★ |

**即使标最高重要度，仍先淘汰过敏。** 因为它从没被命中过。

### 2.3 根因

抽取 prompt 里的 `importance` 只有「1-5」两个字符，**没有任何关于「失效代价」的说明**：

```
{"facts": [{"content": "...", "importance": 1-5}]}
```

模型只能按「这条信息多重要」猜，而这个分数之后还要乘以「衰减」并与「命中次数」竞争。

### 2.4 修法（最小、最保守）

只扩 `protected()` 加一维「失效代价」判据，**不动**权重公式、**不动**淘汰排序、**不动** FACTS_MAX：

```python
_CRITICAL_PATTERNS = (
    '过敏', '忌口', '禁用', '不能吃', '不能碰', '不可吃',
    '用药', '服药', '病历', '病史', '身份证', '密码', '紧急联系',
)

def is_critical(f):
    text = (f.get('content') or '')
    return bool(text) and any(p in text for p in _CRITICAL_PATTERNS)

def protected(f):
    if f.get('pinned'):              return True
    if _mev.is_identity_entry(f):    return True
    return is_critical(f)            # ← 新增
```

### 2.5 修复后

| 检查 | 修前 | 修后 |
|---|---|---|
| 「对花生过敏」protected | ★ 否 | **✓ 是** |
| 「青霉素过敏」 | ★ 否 | **✓ 是** |
| 「服用降压药，不能吃葡萄柚」 | ★ 否 | **✓ 是** |
| 「身份证号后四位」 | ★ 否 | **✓ 是** |
| 过敏 vs 20 次命中周杰伦（cap=1） | 淘汰过敏 | **淘汰周杰伦** |
| 普通条目（周杰伦/火锅/matplotlib） | 可淘汰 | 仍可淘汰 ✓ |

### 2.6 6 项测试 + 真锁验证

回退 `protected` 里的 critical 判据后：

```
test_critical_entries_are_protected            ✗ 未受保护
test_critical_beats_frequent_competitor        ✗ 淘汰了关键条目
test_critical_not_affected_by_importance       ✗ imp=1 时未保护
⇒ 3 failed（真锁）
恢复后 ⇒ 5 passed
```

### 2.7 我刻意没做的两件事

**① 词表取窄，宁可漏**

「考研目标是西南大学」「底线是不熬夜」这类失效代价也高，但词表**故意没收**。
理由：这是**产品策略**（"什么记忆永远不能丢"），不该由我单方面拍。
`test_critical_known_gap_is_documented` 专门锁住这个缺口——将来扩表时它会红，提醒同步更新注释。

**② 不加「imp=5 且从未命中就不淘汰」这条间接规则**

听起来很美（高分+没被用过=潜在关键），但它会误保护所有被标高分却没被用过的条目，
长期会让保护范围膨胀、淘汰失效。宁可漏，不可滥。

## 三、它说的一条我需要核对（结论：表层不准，深层对）

桌宠说：

> 「系统里只有"加"和"删"，没有**"这条取代了那条"**。」

**核对结果**：

| 检查 | 结果 |
|---|---|
| `status='superseded'` 机制 | **存在**，真实库 23 条 |
| `superseded_at` 字段 | 5 条有值（其余是历史遗留） |
| `superseded_reason` 字段 | 5 条有值 |
| **指向「被谁取代」的字段** | **0 条（不存在）** |

⇒ **机制存在，但只有「被推翻」标记，没有「取代链」。**

它的**深层判断是对的**：知道「A 被推翻了」不等于知道「B 取代了 A」。
现有数据里，「用户喜欢喝冰美式咖啡」被标 superseded，但查不出被哪条取代。

这条不用改代码（功能层面够用），但如果将来要做「你以前可爱吃这个了」这种温度感，
就需要真的取代链。已记入待办。

## 四、它指出但我实验完全没覆盖的三条

这三条不是 bug，是**我的实验设计的盲区**。逐条对照：

### 4.1 「该注入的没注入」是静默的

> 「闸门的代价不是注入了不相关的，而是该注入的没注入——而后者是静默的。」

我的八组实验测了：召回率、注入率、纯噪声、冗余、成本。
**从没测过「本该注入却没注入」的那部分。**

而且它说得对：这类失败**用户感觉不到**。我的「纯噪声 0/3」看起来漂亮，
但那是「没多注入错的」，不代表「没漏掉对的」。

这条要补的实验：构造「必须有记忆才答得出」的问题集，看漏注率。

### 4.2 「注入了但没引用」这个信号

> 「'注入了但没引用'这个信号很值钱：它说明这条记忆在当前语境里是噪声。」

我测了「注入了什么」，**没测「注入了有没有被实际使用」**。
桌宠说这是「最少人做的第三层」，确实——我的实验里完全没有这一层。

⚠ 这条需要真实对话的后续轮次才能判断（模型回复里有没有引用），
我的离线评测做不到。要做得在真实使用中埋点。

### 4.3 「短事实 vs 上下文事实」不该混在一个库里

> 「'上次那个分析'：脱离语境就毫无意义……它其实不是记忆，是指代。」

这条解释了我实验里一个没想通的现象：**注入率随库增长而上升**，
我一直归因为「极值效应」（我记的没错，那是机制），但桌宠给的是**根因**：

如果库里混了大量「脱离语境无意义」的条目，它们在任何话题下都能匹配到点什么
⇒ 注入率当然涨。这不是阈值问题，是**库里混了不该在里面的东西**。

⇒ 这与我实测的「记忆密度 1.2」可以对照：
密度低 = 每条自成一件事 = 很可能包含大量一次性流水（「今天想吃火锅」）。
这类条目本该进 events 层，不该进 facts。

## 五、我对它看法的评价

**它对的地方（3 条，其中 1 条是真缺陷）**：

1. 失效代价维度缺失 —— **真缺陷，已修**
2. 静默漏注比误注入更危险 —— **我的实验盲区，承认**
3. 短事实 vs 指代不该混库 —— **给了我一个现象的根因**

**它不准的地方（1 条）**：说「没有取代关系」，实际有 superseded 机制，
只是没有取代链。它的深层判断仍成立。

**它的核心判断我完全同意**：

> 「剩下的问题几乎都在'怎么定义一条记忆'上——它是什么、什么时候过期、
> 被谁取代、失效代价多大。这些是数据模型问题，不是算法问题。」

对照我这八组实验：前七组都在调**算法**（阈值、检索方式、聚类、标注），
只有第八组（记忆密度）碰到了**数据模型**。而它指出的三条全在数据模型层。

⇒ **它比我更早看到了正确的方向。**
