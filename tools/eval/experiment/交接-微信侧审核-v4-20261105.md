### 5.2 你说的缺陷，我真跑出来了

`_get_scene_img` 改前：

```python
if os.path.exists(pth):
    self.scene_imgs[key] = QPixmap(pth)     # ← 没检查 isNull()
```

实测（构造坏文件 → 换成合法 PNG）：

| 步 | 返回 isNull | 缓存里已写入 |
|---|---|---|
| 第 1 次（坏文件） | **True** | **True** |
| 换成合法 PNG 后 | — | — |
| 第 2 次 | **True（没重读）** | True |

⇒ **一次瞬时加载失败 = 该动作在本次会话内永久失效**，要重启桌宠。

### 5.3 顺带查清了「文件不存在」那条路

我原以为还有「文件不存在 → 不写缓存 → 下次重试」这条良性路径。
查 `asset()` 后发现它**永远返回一个存在的文件路径**（层层兜底到 `{role}_idle.png`），
所以那条良性路径**基本不可达** —— 真正会发生的只有「读成 null 被粘住」这一条。

12 个场景素材我都验了：全部存在、都是 1024×1024、都能读出非 null。
所以正常使用不会触发；触发条件是**加载瞬时失败**（内存压力、杀软锁文件等）。

### 5.4 这也给了 scene 那条测试一个机制

`play_scene` 里：

```python
img = w._get_scene_img(key)
if img is None or img.isNull():
    w.say_plain('这个动作还没准备好~')
    return          # state 留在 idle ⇒ 测试断言 p.state == 'scene' 红
```

**测试红的那一句，正是用户看到「这个动作还没准备好~」的那一句。** 你说的对。

2400 个测试反复建控件（`PetWidget`）时，内存压力下 QPixmap 加载失败一次，
就会被缓存永久化 —— 这能解释「只在超长耗时那一次出现」：
**内存压力大的那次才可能加载失败**。⚠ 这是机制假说，我没有直接证据（没抓到那次的内存曲线），
但比「环境巧合」具体。

### 5.5 修法 + 锁

```python
pm = QPixmap(pth)
if not pm.isNull():
    self.scene_imgs[key] = pm
```

3 项新测试：

| 测试 | 锁什么 |
|---|---|
| `test_null_pixmap_is_not_cached` | 坏文件读成 null 时不许入缓存 |
| `test_recovers_after_transient_load_failure` | **★ 核心回归**：第一次失败、文件修好后必须能读到 |
| `test_all_real_scene_assets_load` | 12 个真实场景键全部能加载（防素材漏配 + 防我改坏） |

**真锁验证**：回退 ⑤（把 null 也存进缓存）⇒ **2 红**；恢复后 **10 绿**。
