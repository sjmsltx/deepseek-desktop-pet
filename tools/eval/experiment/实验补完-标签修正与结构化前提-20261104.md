1. **上一份注入报告的结论作废**：它用的标签有严重错误（内容不同的事被塞进同一个 topic）。

## 一、作废了什么：错标签

### 1.1 错在哪

上一版标签（`library-labels.json`，v1）给模型一张 86 项的 topic 候选表，模型为避免新建标签，
把内容不同的事硬塞进就近的桶。抽查证据（真实库 + 合成库）：

| 原文 | 被标 topic | 应属 |
|---|---|---|
| 用户喜欢小型户外婚礼 | **个人身份** | 婚礼 / 婚恋 |
| 用户对科目一的想法从"想赶紧考完"变成… | **个人身份** | 驾考 |
| 线性代数作业里的分块矩阵求逆卡了半天 | **Python学习** | 线代作业 |
| 练大地测量挺久了，一学期每周整理观测记录 | **Python学习** | 大地测量 |
| 用户原本喜欢一次多充话费 | **健康管理** | 话费 / 消费 |
| batch 0（遥感原理课程 5 条） | **地理数据分析** | 遥感原理 |

**机械抽查**：1411 条里 178 条（12.6%）aspect 与文本矛盾
（如 `aspect=habit` 但没有「坚持/一直/每周」这类持续词）。

### 1.2 为什么会出现

`label_library.py` 给了 topic 候选表。模型的合理策略是「尽量复用」，于是产生**吸附**：
batch 0 的「遥感原理」被「地理数据分析」吸走，batch 2 的 7 条不同内容也全进同一个桶。

⇒ 这是**我上一轮建议「给候选表提高复用率」的直接代价**。当时测出复用率 100% 就判它好，
没测「同 batch 内 topic 是否唯一」——那是真正的归并正确性指标。缺了这个指标，错的东西看起来很好。

## 二、标签修了三版，前两版都不行

| 版本 | 做法 | 同 batch topic 唯一率 | topic 总数 | object 覆盖 |
|---|---|---|---|---|
| v1 | 给 86 项 topic 候选表 | **59.4%** | 86 | 4.1% |
| v2 | 完全不给候选表（自由命名） | **26.4%** | 618 | 4.1% |
| **v3** | **按对话分组标注** | **100%** | 239 | **88.5%** |

### 2.1 v2 为什么更差

自由命名导致过碎：同一段对话的 5 条记忆，模型给了 5 个不同的 topic 名字
（「编辑器偏好」「编辑器使用习惯」「编辑器配置调整」…）。

### 2.2 v3 为什么对

**标注单位错了**，不是给不给候选表的问题：

```
❌ 逐条标：每条记忆各自决定 topic ⇒ 同一段对话里的 5 条会得到 5 个 topic
✅ 按顿标：一段对话先命名一个 topic，再给其中每条分配 aspect
```

「一件事的多个面向」这个概念本身就是「一个实体 + 多个 aspect」——
所以正确顺序是先定实体（按对话），再定面向（逐条）。

v3 抽样验证（命名质量）：

```
batch 0   → topic='遥感原理学习'   object='遥感原理'
   [preference] 喜欢遥感原理课程，认为比 GIS 编程更有意思
   [change    ] 对遥感原理的看法发生变化：以前觉得太理论，现在觉得做项目挺实用
   [habit     ] 坚持每周整理遥感原理笔记已快一学期
   [struggle  ] 公式推导有时会卡住，需要慢慢磨
   [advice    ] 学长建议多看看城市热岛方面的案例

batch 57  → topic='鱼香肉丝口味'   object='鱼香肉丝'
   [preference] 特别爱吃鱼香肉丝，喜欢酸甜辣口
   [preference] 吃鱼香肉丝有固定讲究：木耳和笋丝必须有
   [habit     ] 这个习惯已保持好多年，从大学食堂到现在
   [change    ] 近期口味有变化：以前重油重辣，现在清爽点
   [episode   ] 前两天跟同事聊过鱼香肉丝
```

五个面向齐全，命名准确。**v3 的 object 覆盖从 4.1% 提到 88.5%** —— 因为
「一段对话围绕的对象」比「单条记忆的对象」更容易判定。

### 2.3 v3 也有一个坏消息

同 batch 唯一率 100% 是**恒真**的：topic 就是 batch 的别名，跨 batch 数量为 0。

试了把多段对话合并成同一实体（按 object 相同、按 topic 同名、按向量相似度：
相似度中位只有 0.322，阈值 0.96 只合并了 3 对，239 → 232）。

⇒ **在这份合成数据上，「跨对话的同一实体」几乎是伪命题** ——
1411 条来自 239 个不同种子，本来就没有重复话题。

## 三、真正的问题：真实库有没有可归并的东西

### 3.1 结构化要产生价值，前提是「同一件事有多条记忆」

如果库里每件事只有一条，聚合 = 原样输出，白做。

实测三种口径：

| 数据 / 口径 | 条数 | 实体数 | 平均每组 | **单体占比** | 聚合后留存 |
|---|---|---|---|---|---|
| 合成库 按 batch | 1411 | 239 | **5.9 条** | 0% | 0.17 |
| 合成库 按 topic | 1411 | 239 | 5.9 | 0% | 0.17 |
| 合成库 按 object | 1411 | 235 | 6.0 | 0% | 0.17 |
| **真实库 LLM 分组** | 21 | 18 | **1.2 条** | **83%** | **1.00** |
| 真实库 v3 topic | 21 | 18 | 1.2 | 83% | 1.00 |
| 真实库 按 object | 21 | 18 | 1.2 | 83% | 1.00 |

### 3.2 结论

**真实库里 83% 的组是单体**（15/18 组；按**条数**算 71%，即 15/21 条）。
（21 条 → 18 个实体，平均 1.2 条/件。两个数都对：83% 是组维度，71% 是条维度，
引用时必须说清是哪个——WX-178 §五 指出我原文写成「83% 的记忆」，容易被读成条维度。）
聚合后留存 1.00 = 原样输出，没有任何压缩。

而合成库平均 5.9 条/件 —— 那是**人为造出的高密度**：1411 条是按
「一段对话产生 5~9 条同一件事」的方式批量生成的。

⇒ **我之前用自己造的合成数据，量出了一个真实场景里不存在的收益。**

### 3.3 这解释了前两轮所有反常现象

| 现象 | 真实原因 |
|---|---|
| 合成库 M2 聚合后成本反而更长（91 → 127 字） | 实体大（5.9 条），聚合句必然长 |
| 真实库 M2 成本 88 → 35 字（看起来省了） | 因为错标签把 21 条并成 1 个实体（假收益） |
| 真实库 M2 召回从 11/12 掉到 8/12 | 同上：全并成一个实体后，聚合句盖不住具体答案 |
| 「冗余 0.58 → 0.00」 | 冗余确实降了，但那是**把多条并成一条**的必然结果，不是额外收益 |

## 四、那多维节点到底还做不做

### 4.1 数据说：在真实使用密度下，不值得为注入做

| 判断项 | 数据 | 含义 |
|---|---|---|
| 真实库单体占比 | 83% 的组 / 71% 的条 | 大多数记忆无可归并对象 |
| 真实库平均每组 | 1.2 条 | 聚合几乎不省字 |
| 聚合后留存 | 1.00 | 没有压缩 |
| 召回 | 结构化反而降（8/12 vs 11/12） | 归并错了会盖掉具体答案 |

### 4.2 但有一个前提会变：记忆密度会随使用上升

现在真实库是 3 个月攒的 21 条。如果：
- 使用年限拉长（Owner 说的「十几年」）
- 同一件事被反复提及（「爱吃桃片」会被提很多次）

那么单体占比会下降。**这个拐点在哪，需要真实数据才知道。**
现在能做的不是猜，而是**建一个可观测指标**：

```
记忆密度 = 平均每件事的记忆条数（= 条数 / 实体数）
```

加到 `memory_fact_evict.capacity_status()` 里，和淘汰台账一起观测。
当密度超过某阈值（比如 2.0）时，结构化才值得做。

### 4.3 建议的结论

| 事项 | 建议 |
|---|---|
| 多维节点（为注入省字） | **暂缓**。等记忆密度观测到 >2.0 再说 |
| `aspect` 字段 | 可以留（成本低，且对「这条是什么面向」有解释力），但**不参与注入决策** |
| 实体归并 | **不做**。真实场景 83% 的组（71% 的条）无可归并对象 |
| 向量检索 | 仍然值得（召回 3/12 → 11/12），与结构化无关 |

## 六、本轮我犯的错（4 条）

| # | 错误 | 后果 | 修法 |
|---|---|---|---|
| 1 | 给 topic 候选表后只看复用率（100%）就判「好」 | 没测同 batch 唯一率（59.4%），错标签流进了注入实验 | 加「同 batch topic 唯一率」指标 |
| 2 | 逐条标 topic，而不是按对话标 | v2 更差（唯一率 26.4%、topic 618 个） | 改成按对话分组标注（v3） |
| 3 | **拿自己造的高密度合成数据，推真实场景的收益** | 「聚合省上下文」在真实库不成立（单体 83% 的组 / 71% 的条） | 用真实库密度做判据，合成库只当上界 |
| 4 | 真实库用了与合成库不同的标注口径（逐条 vs 分组） | 21 条并成 1 个实体，召回假降 | 真实库单独做分组标注 |

第 3 条最该记：**合成数据的分布是我定的，用它的高密度去证明结构性收益，等于自证**。
判据必须来自真实数据。
